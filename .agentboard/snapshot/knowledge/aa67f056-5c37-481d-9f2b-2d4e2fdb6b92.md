## 结论
设置页「猫猫旅行 → 自动回收」开关读写 `settings.travelAutoRecover`（默认 true），`PATCH /api/settings` 即时生效、无需重启服务；回收 ticker 每轮实时读 settings。

## 实现口径（SETTINGS-TRAVEL）
- 前端独立分区 `TravelAutoRecoverSection`，与「服务与并发」表单解耦：自己 `useQuery(['settings'])` 读、`useMutation` PATCH 只发 `{ travelAutoRecover: next }`，成功后失效同 key 缓存，不参与底部「保存」按钮的 dirty 判定。
- 后端字段定义在 `config.ts`（默认 true、布尔校验、持久化到 config.json）；PATCH schema 允许可选布尔；关闭时 ticker 整轮跳过。
- 文案：派出后约 3 小时 45 分自动回收（4 小时窗口内有效），关闭后不再自动回收。

## 验证
- 前端组件测试 3 例：默认 true 显示开启、点击 PATCH body 精确、500 保留原值并报错；`pnpm --filter @agentboard/web test -- TravelAutoRecoverSection`。
- 后端契约：`pnpm --filter @agentboard/server test -- travelRecovery.test.ts settings.test.ts`（默认 true + PATCH 接受布尔）。

## 坑（踩过）
已在运行的服务进程若不包含新字段，会表现为：`GET /api/settings` 响应里没有 `travelAutoRecover`（前端回落显示 true），`PATCH {"travelAutoRecover":false}` 直接 400 `VALIDATION_ERROR：至少提供一个更新字段`。此时不要怀疑前端，需要重启服务进程后才能真正端到端验证；旧代码路径本身没有该字段的写入口。
