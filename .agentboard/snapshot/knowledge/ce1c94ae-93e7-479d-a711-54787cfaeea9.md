## 抽取动因

四个 CLI 适配器（codebuddy / codex / opencode / dsh）的 `runTurn` 骨架逐字同构：
`eventCbs` 数组、`settled` 幂等、`killed` 标记、`finish(code)` 归一退出码、
「stderr 有内容且（非零退出 或 exit 0 零事件无 session id）」时补一条诊断 error。
复制四份的代价是修一处诊断规则要改四个文件，且新增适配器必然再抄一遍。

## 骨架契约（packages/adapters/src/turnRunner.ts）

- `createTurnRunner({ sessionId, onFinish })`：`sessionId` 是取值函数（行解析中途可能写入）；
  `onFinish` 是**个性化终局钩子**，返回 `{ exitCode?, errors?[] }`，错误事件在通用 stderr 诊断之前发出。
- `finish(code)` 幂等：首个退出码生效；退出码 `code ?? -1`（被信号终止归一为 -1）；
  `TurnResult` 带 `adapterSessionId` 与非空 `stderrTail`。
- `bindChild` 绑定主进程（stderr 尾部来源 + kill 目标）；`bindKillTarget` 登记额外 kill 目标
  （dsh 的 `--version` 版本探针就靠它，kill 时探针与主进程都会被终止）。
- `markEvent` 记录「收到结构化事件」，用于抑制 exit 0 零事件的诊断噪音；`getChild` 供 codebuddy 的
  answer 回填 stdin；`isSettled` 供 ask 登记门禁用。
- 个性化部分留在适配器：参数拼装、行解析、channel 状态机。codebuddy 的「图片轮次 exit 0 但无模型文本」
  在 `onFinish` 里改写为 `exitCode=-1` 并追加可读错误，与抽取前行为一致。

## spawn 形态缓存（packages/adapters/src/spawn.ts）

- `resolveSpawnForm(cmd)` 结果按逻辑命令做**进程级缓存**：每轮 turn 都要探测会白起一个 `where` 子进程。
- **只缓存探测成功**（`where` 输出非空）：用户先装 CLI 后装好，下一轮仍能重新探测；失败走原样 spawn。
- `setSpawnFn`（测试注入点）会清空缓存，测试之间天然隔离；`resetSpawnFormCache()` 用于同一用例里
  「换了一套 where 结果」的场景。

## 坑

- 同一测试里先让 `where` 成功、再切失败，若不清缓存会继续用第一次解析出的形态（opencode.test 已按
  新语义调用 `resetSpawnFormCache()`）；这不是回归，是缓存的预期行为。
- 适配器文件的 `UnifiedEvent` 类型在骨架抽取后仍需显式 import（只用于局部数组/回调签名），
  删 import 会撞 TS6133。
- 缓存不做过期：进程内 CLI 被卸载/升级后仍用旧路径，`spawn` 失败由 close/ENOENT 归一，不影响 turn 收尾。
