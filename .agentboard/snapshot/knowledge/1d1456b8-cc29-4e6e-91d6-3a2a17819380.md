# 现象与根因

界面点「切换」报「参数不合法」（REASON_LABEL.VALIDATION_ERROR 的通用文案），用户以为前端发错参数。真机复现证据链（2026-11-08，测试页 5174 + 真服务）：

- 请求：POST /api/managed-accounts/<id>/switch，body `{}`（前端无参数问题）。
- 响应：400 `{"error":{"code":"VALIDATION_ERROR","message":"账号与产品/实例不一致"}}`。

根因链（三层叠加）：

1. **账号来源决定 client_instance_id 语义**：capture 线账号存当前机器实例哈希；协议授权线存字面量 `protocol`；导入线存字面量 `imported`。
2. **workbuddy provider 切换传的是当前实例哈希**（`workbuddyDesktopProvider.switchAccount` 入参 `client_instance_id: this.instanceId`，锁与 recovery 门禁都按真实实例作用域，这是正确的，不能改成账号自身值）。对协议/导入线账号，`createAccountOperation` 的库级三元组校验（`accountOperation.ts:13`：managed_account 的 id+app_id+client_instance_id 必须与入参一致）必然失败，抛**通用 ValidationError**。
3. **前端把 VALIDATION_ERROR 映射成「参数不合法」**，把域语义错误（实例不匹配）伪装成参数格式错误。

minimax/trae provider 无此问题：它们传 `account.client_instance_id`，实例不匹配由各自 preflight/validate_target 以 409 域错误码处理。

# 修复口径

- provider 入口预检（修在 workbuddy switchAccount 顶部，不改库级校验、不改锁语义）：账号存在且 app 匹配但 `client_instance_id !== this.instanceId` → 直接 409 `TARGET_INSTANCE_MISMATCH`（SAFE_ERROR_CODES 已收录、前端已有中文映射「目标账号实例不匹配」），不建操作行、不触碰客户端。
- 路由 `:id` 补 UUID 校验（对齐同域 refresh-credential/restore/PATCH/delete）：非 UUID → 400 VALIDATION_ERROR「id 必须为 UUID」。
- 复现与验证手法：页面注入 fetch 钩子（wrap window.fetch 记录 url/body/status/响应体）→ 浏览器实际点击 → 卡面留证据链；真服务三探针（非 UUID 400 / 不存在 UUID 404 / 协议线账号 409）。

# 坑

- UI 就地确认行（切换/删除）3 秒自动收回：跨工具调用的思考间隙必然超时，自动化要点开+确认必须在同一次页面执行上下文里完成（原生 `el.click()` + 微任务等待 + `el.click()`；CDP 坐标点击单次耗时可超 3s，不可靠）。
- `GET /api/account-operations` 无 path id 时是另一个端点（要求 batch_id），别与 `GET /api/account-operations/:id` 混淆。
