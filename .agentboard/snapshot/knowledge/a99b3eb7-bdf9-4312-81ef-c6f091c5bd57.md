# Web HTTP 客户端超时（CR-2）

## 契约

- `apps/web/src/api/client.ts` 的 `request`（GET/POST/PUT/PATCH/DELETE 共用）超时 **15s**；`uploadAttachment` 单独 **60s**。两者都通过内部 `fetchWithTimeout` 实现，调用方签名（`api.get/post/...`、`api.uploadAttachment`）不变。
- 超时抛 `ApiError(message='服务无响应，请稍后重试', code='TIMEOUT', status=0)`。`status=0` 与服务端 HTTP 错误（≥400）可区分；`apps/web/src/lib/errorCodeText.ts` 已登记 `TIMEOUT` 中文文案，`ErrorState` 横幅据此展示「服务无响应，请稍后重试」，不会表现成普通失败。
- 非超时的网络错误（如 `TypeError: Failed to fetch`）原样抛出，不伪装成 TIMEOUT。

## 取值取舍

- 普通请求 15s：MCP 客户端取 10s，web 首屏会串行发多条查询（workspaces → statuses → issues），留更宽松余量，避免慢而健康时误报。
- 上传 60s：上传要读本地图片 + 服务端落盘写入，时间尺度与普通 GET 不同，不能共用 15s；但仍必须有上限，否则服务端卡死时上传按钮永久转圈。

## 实现坑（实测，别再用 AbortSignal 传 fetch）

最初按「AbortSignal.timeout 传给 fetch」实现，`pnpm --filter @agentboard/web test` 直接 **94 个测试文件 / 620 条用例全红**，报错：

`TypeError: RequestInit: Expected signal ("AbortSignal {}") to be an instance of AbortSignal.`

原因是 jsdom 的 `AbortSignal` 与 undici（Node fetch）的 `RequestInit` 校验跨 realm，不是我们的代码错——但会造成全量门禁失效。

现行实现：`Promise.race([fetch, setTimeout → reject TIMEOUT])`。到点立即解除 loading；底层请求不主动取消（由浏览器/网关自行回收），并对 fetch promise 挂空 catch 防 unhandled rejection。若将来要真正中断连接，只能在浏览器产物里用 signal，并为测试环境补 realm 适配，不要直接套用到 jsdom 套件。

## 验证方法

- 单测：`pnpm --filter @agentboard/web exec vitest run src/test/clientTimeout.test.tsx`（覆盖 15s/60s 各自到点、非超时错误透传、DOM 横幅文案）。
- 真实假服务探针：`node:http` 起一个只监听不回包的 server，把相对路径 fetch 包装到该端口，`api.get` 在 **15019ms** 抛 `code=TIMEOUT, status=0, message=服务无响应，请稍后重试`（探针用完即删，不入库）。
