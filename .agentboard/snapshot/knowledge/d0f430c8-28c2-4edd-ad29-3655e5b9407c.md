# CLI 引用解析瘦身：fields 白名单与决策批量读（CR2-10）

## 结论

- 短前缀解析（`kb show/close/... <≥8 位前缀>`）与 404 纠错都要扫全部工作区的任务列表。扫描只取定位字段
  `fields=id,workspace_id,title,status`，唯一命中后再 `GET /api/issues/<id>` 取完整 Issue —— 调用方（show/accept/close）
  依赖 description 与 comment_count，不能直接把裁剪后的对象返回。
- 实测同一工作区任务列表：完整字段 **1,918,198 B** → fields 白名单 **160,681 B**（约 8.4%）。
  复算：node 下 fetch 该工作区 `/api/issues`（带与不带 fields），取响应 Buffer 字节数。
- 服务端 `GET /api/decisions` **没有游标/offset**；repo 在缺省 limit 时只回 **200 条**（apps/server/src/db/repos/decision.ts:287）。
  因此决策前缀解析要么显式传一个足够大的 limit（当前 100000），要么永远有假阴性。不要用「不传 limit 拿全量」——
  那是 200 上限，不是全量。
- 决策前缀解析用一次 `GET /api/decisions?workspace_ids=a,b&limit=N` 批量读，替换逐工作区串行扇出；单区失败不拖垮整体。
- 测试桩连带影响：前缀唯一命中后会多发一次 `GET /api/issues/<full-id>`，旧的 ids-file 桩必须补这条，否则 exit 1。
- `kb decision` 不是单层命令：详情是 `kb decision show <id|前缀>`，测试里写成 `['decision', id]` 会落到未知子命令。

## 为什么这样修

- fields 白名单是服务端既有能力（`ISSUE_FIELD_NAMES` 白名单，默认开启），CLI 只需在扇出 URL 上带 `fields`，无需服务端改造。
- 决策侧服务端缺分页能力，客户端无法续拉；在「不改服务端」的约束下，显式大 limit 是一次性读全的唯一可行路径，
  且前缀解析是低频人工操作，代价可接受。若未来决策量级上到十万级，应在服务端补 offset/cursor 再改回分页。
