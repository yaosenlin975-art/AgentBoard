# /api/issues 分页缺省字段裁剪契约（PERF-4）

## 契约
- `GET /api/issues` 的 `fields=` 是白名单：未知名 → 400。
- **分页模式**（带 `limit` 或 `offset`）且**未显式传 `fields`** 且 V2 开启：缺省套 `DEFAULT_PAGE_FIELDS`（26 个展示字段：id/workspace_id/title/priority/labels/status/sort_order/claimed_by/claimed_at/session_id/parent_issue_id/due_date/due_time/comment_count/dependency_violation/decision_locked/open_decision_id/decision_grace_until/decision_waiting_seconds/blocked_by_count/blocked_by_open_count/resolved/created_at/updated_at/children_total/children_closed）。**不含 `description`**。
- **非分页模式**（无 limit/offset）缺省仍返回完整字段（含 description），保持旧契约，避免读详情的老调用方断。
- 显式 `fields=description` 时才做正文窗口：默认截取 12000 字符，附 `description_truncated` 与 `next_description_offset_chars`。
- `GET /api/issues/counts?workspace_ids=…` 按状态聚合，与全量列表逐状态一致；缺参/重复/未知工作区/超 50 个均为 4xx。

## 为什么要这样切
- 列表页 payload 主要在 description 正文；100KB 阈值下，把正文从列表缺省里拿掉最有效且不改存储。
- 实测（隔离实例 + 当前构建，8 个工作区）：`?workspace_id=e41eb0fb…&limit=50` 从 **117,133 B** 降到 **35,179 B**（三次 16–37ms），所有工作区最大 35,179 B；非分页 90 条约 190KB 属老契约，未改。

## 踩过的坑（测试口径）
- `apps/server/test/pagination.test.ts` 原来断言「分页缺省 items[0].description 存在且被截断到 12000」，这是旧契约；裁掉缺省字段后必须同步改为「缺省无 description」，另发一条 `fields=id,description` 验证窗口行为，否则会出现真回归。
- 服务端全量 `vitest run` 存在**跨文件相互干扰**的假失败：本次串行全量 8 文件 24 条失败，其中 `gitOnDone.test.ts` 单文件复跑 **26/26 通过**（69s）。判断某条失败是否真回归，先单文件复跑；不要用全量结果直接归因。

## 影响面
- 依赖分页缺省 description 的前端/脚本需显式加 `fields=description`（或改用详情接口）。
- 非分页调用方无感。
