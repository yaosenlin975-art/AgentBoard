# WorkBuddy 猫猫旅行派出后自动回收（TRAVEL-REC）

关联契约页：workbuddy-travel-status-contract（状态判定与 claim/depart 回查口径不重复，本页只写自动回收）。任务链：03e6da6f（总卡）/ 0df1a242 / 4a0cb507 / 0790a724。

## 为什么需要

签到成功后的猫猫旅行分派出与回收两步：派出后在 **4 小时**内回收才得分，超时该轮作废。原本 `afterCheckin` 只把结果写进 `account_operation.recovery_ref` 文本（`travel=dispatched`），没有轮次 id / 派出时间 / 到期时间，进程重启即丢，用户必须人工盯回收。

## 状态机与持久化

- 新表 `workbuddy_travel_round`（纯追加迁移，`initSchema` 幂等）：`state ∈ pending|claimed|missed|failed`、`dispatched_at`、`due_at`、`attempts`、`last_attempt_at`、`safe_error_code`、`operation_id`。
- 唯一约束：每账号至多一条 `pending`（部分唯一索引）；重复记录 `INSERT OR IGNORE`，不重置 `due_at`，保证同一轮只回收一次。
- 状态流转走 CAS（`UPDATE … WHERE id=? AND state='pending'`，`changes=1` 才算成功），超窗与并发 tick 都不会重复回收。
- 派出成功（`afterCheckin` → `dispatched`）时 runner 落 pending；`claimed/already_done` 不建行。本地记录失败不回滚签到结果，只在 `recovery_ref` 追加 `:record_failed` 留痕。

## 时间口径（已固化在 `db/repos/travelRound.ts`）

- `TRAVEL_SCORE_WINDOW_MS = 4h`：得分窗口上限。
- `TRAVEL_SAFETY_MARGIN_MS = 15min`：给请求延迟与时钟误差留余量。
- `TRAVEL_RECOVERY_DELAY_MS = 225min`（3 小时 45 分）= 到期回收时刻 `due_at = dispatched_at + 225min`。
- `TRAVEL_SWEEP_INTERVAL_MS = 5min`：扫描周期。

## 回收执行（`services/accounts/travelRecovery.ts`）

- `sweepTravelRecoveries`：先判超窗（`now >= dispatched_at + 4h`）→ 直接 `missed` + `TRAVEL_WINDOW_EXPIRED`，**不发请求、不假装成功**；再处理 `due_at <= now` 的 pending。
- 回收动作是 provider 的新可选方法 `claimAfterTravel`：只 status→claim，**绝不重新 depart**；`idle` 视为轮次已结束（`already_done`），不把旧轮次当新一轮。`afterCheckin` 与它共用 `claimTravel`（claim 后必须回查确认）。
- 结果映射：`claimed/already_done` → `claimed`；`dispatched` → 保留 pending，`safe_error_code=TRAVEL_STILL_TRAVELING`；`failed`/异常 → 保留 pending，`attempts+1` 并写错误码（`TRAVEL_RECOVERY_FAILED:<ApiError 码>`、`TRAVEL_CREDENTIAL_MISSING`、`TRAVEL_ACCOUNT_DISABLED` 等），下轮重试直到超窗。provider 未实现该方法 → 终态 `failed` + `TRAVEL_RECOVERY_UNSUPPORTED`（不空转）。
- `startTravelRecoveryTicker`：启动立刻跑一次补偿扫描（启动补算），之后每 5 分钟一轮；启动与周期 tick 通过 promise 链串行，避免同批行被并发处理；默认 `setInterval` 调用 `unref`，不阻塞进程退出。

## 接线与开关

- `createApp` 在注入 workbuddy 签到 provider（`checkinProviders.workbuddy_desktop` 或兼容的 `checkinProvider`）时启动 ticker，句柄挂 `CreatedApp.travelRecovery`（`ready`/`runNow`/`stop` 供验证）；`travelRecovery: false` 显式关闭。
- 开关 `settings.travelAutoRecover` 默认 `true`，ticker 每轮实时读 `readSettings()`；关闭时整轮跳过、不改任何行；`PATCH /api/settings` 后无需重启。
- 查询端点 `GET /api/travel-recoveries?state=&limit=` 暴露轮次状态（脱敏，无凭据 ref/token）；`missed` 行即「已错过」的如实上报。

## 验证要点（复算）

- `npx vitest run test/travelRecovery.test.ts`（服务 + 接线 + HTTP，14 用例）。
- 接线（RULE-3）：createApp 用例断言启动补偿真调 provider、轮次落 `claimed`、调度器收到 `5*60*1000`、`stop` 触发 cancel、再次 `runNow()` 的 `attempted=0`。
- 迁移幂等：`npx vitest run test/travelRound.test.ts` 断言两次 `initSchema` 后 4 条 DDL 不变。

## 注意

- 本功能不改变签到成功判定与批次状态机；旅行回收失败不影响已完成的签到记录。
- 快照只会出现在 `account_operation.recovery_ref`（文本留痕）与本表（结构化状态）两处，不含凭据。
