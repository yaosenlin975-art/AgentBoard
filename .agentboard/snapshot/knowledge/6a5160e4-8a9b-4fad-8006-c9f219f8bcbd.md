# 卡片「如何验收」区块：契约与交互设计（proposed）

> 状态：设计稿，未落地。实现前不得当作已存在能力引用。

## 1 目标与非目标

### 目标

- 每张卡自带一块**照着点就行**的验收内容，验收人不用在散文里找判据、不用自己对照命令。
- 验收信息**结构化到可渲染、可逐条勾、可生成结论**，避免退化成又一段散文。
- 自动化门禁与人工目视两种验收**并存于同一张卡**，并显式区分「机器判」与「人眼判」。
- 执行 agent 写卡时就顺手填好；执行期间标准被冻结，改了要留审计痕迹。
- 存量卡可**按需**迁移，不一次性自动改写 271 张卡。

### 非目标 / 反目标

- 不做通用表单引擎（自定义字段、条件分支、嵌套分组）。
- 不在看板里执行命令；「自动项」是给人跑的指引，不是测试运行器。
- 不替代 `kb accept` / `kb close` 的结论与状态语义。
- 不做验收评分、通过率仪表盘、跨卡汇总。
- 不是「验收模板市场」，不引入继承/复用机制。

## 2 现状核查（事实）

### 2.1 数据面

- `issue` 表**没有 notes 列，也没有验收列**：字段为 id / workspace_id / title / description / priority / labels / status / sort_order / 占用与租约四列 / parent_issue_id / due_date / due_time / created_at / updated_at。
- 验收标准今天实际写在 `issue.description` 的 markdown 里（新建卡模板为「目标 / 范围 / 验收 / 边界」，智能草稿渲染为「背景 / 要求 / 验收」三段）。
- 统计（工作区 e41eb0fb 全量 727 张卡）：描述含「验收」字样 622 张，含独立 `## 验收` 段 271 张；当前待验收 57 张、待规划 21 张。也就是**多数卡只有零散验收描述，只有约三成有可定位段落**。

### 2.2 执行与结论面

- `kb done --notes`：notes 非空时以 `agent:<id>` 身份**落一条普通评论**，不结构化。
- `kb accept --verdict pass|fail --note`：写固定格式评论 `【验收记录】verdict=…; reviewer=…; at=…`，第二行起是散文依据；**只记录、不改状态**，关闭仍走 `kb close`。
- 结论因此散在评论流里，无法按条目对照，也无法判断「3 条判据过了几条」。

### 2.3 展示面

- 详情面板顺序：字段区（MetaRow → 创建时间 → 决策区 → **描述** → **标签**）→ 依赖 → 评论 → 折叠区（关联会话 / 附件 / 原始 JSON / 审计证据）→ 吸底操作条。
- 看板卡片只渲染：标题、优先级色条、截止徽标、标签、决策标记、占用徽标、评论数。
- 结论：验收信息在详情里**混在描述这张长文里**，在列表上**完全不可见**。

## 3 方案对比与选定

| 方案 | 做法 | 代价 | 主要问题 |
| --- | --- | --- | --- |
| A 纯约定 | 只规定 description 内 `## 验收` 的 markdown 子结构（`- [ ] 步骤` + 判据），渲染时增强 | 零 schema 改动 | 结构靠自觉，半年后必然退化回散文；无法做板卡标记与门禁；与「避免退化」目标直接冲突 |
| B 子表 | 新建 `issue_acceptance_item` + `acceptance_run`，逐条落库、勾选态共享 | 迁移 + 三端 + 权限 + 测试，最大 | 首版过度设计：多人协同勾选是**尚未出现**的需求，却要立刻付出状态机与权限成本 |
| C 单 JSON 列（选定） | `issue.acceptance` 存版本化 JSON（前置 + 条目数组），校验走 zod；勾选态 v1 只做本地辅助，结论仍用 `kb accept` | 一列 + 三端渲染 | 勾选态不共享（v1 明确接受，升级路径见 §9） |

选 C 的理由：结构化收益（可渲染、可勾、可 lint、可门禁）在单列内就能拿到；把真正昂贵的部分（共享勾选、逐条落库）推迟到需求出现后再加，且升级时 JSON 结构可原样搬进子表，不需要重新设计契约。

## 4 字段定义（acceptance v1）

单列 `issue.acceptance TEXT NULL`，内容为 JSON；空/NULL = 未填写。序列化上限 8 KiB（防止把描述整段搬进来）。

```json
{
  "version": 1,
  "kind": "mixed",
  "preconditions": [
    { "text": "分支已切到 feat/acceptance-block", "check": "cmd:git rev-parse --abbrev-ref HEAD" }
  ],
  "items": [
    {
      "id": "v1",
      "kind": "auto",
      "action": "npm run check:all",
      "expect": "EXIT=0，57 项全绿",
      "failIf": "任一 ✖ 或脚本数变化",
      "evidence": "terminal"
    },
    {
      "id": "v2",
      "kind": "manual",
      "action": "1440×900 打开待验收卡详情",
      "expect": "「如何验收」位于描述与标签之间，复选框可点，无横向滚动",
      "evidence": "screenshot"
    }
  ]
}
```

### 4.1 字段表

| 字段 | 必填 | 约束 | 说明 |
| --- | --- | --- | --- |
| `version` | 是 | 仅接受 `1` | 未知版本在装载期报错并拒绝渲染，**不静默降级** |
| `kind` | 否 | `auto` / `manual` / `mixed`，缺省 `mixed` | 仅用于排序与文案提示，不参与判定 |
| `preconditions[]` | 否 | ≤5 条 | 前置状态：环境、分支、数据、账号等「不满足就不该开始验」的条件 |
| `preconditions[].text` | 是 | ≤80 字 | 一句话状态描述 |
| `preconditions[].check` | 否 | `cmd:` 前缀 | 可复制的自查命令，只展示不执行 |
| `items[]` | 是 | 1–12 条 | 验收条目；>12 说明这张卡该拆 |
| `items[].id` | 否 | `^[a-z][a-z0-9]{0,7}$`，卡内唯一 | 缺省由服务端按顺序生成 `v1…vN`，禁止手写重复 id |
| `items[].kind` | 是 | `auto` / `manual` | 机器判 / 人眼判，决定渲染形态与证据默认值 |
| `items[].action` | 是 | ≤200 字 | 操作步骤；`auto` 项就是一条可复制命令 |
| `items[].expect` | 是 | ≤200 字 | 观察点 = **通过判据**，必须写成可观察结果（数字、文案、状态、可见/不可见） |
| `items[].failIf` | 否 | ≤120 字 | 不通过判据；缺省语义为「未满足 expect 即不通过」 |
| `items[].evidence` | 否 | `none` / `terminal` / `screenshot` / `json` | 证据要求；缺省 `auto → terminal`、`manual → screenshot` |

**不引入的字段**（刻意留白，防止长成测试框架）：任意脚本、正则断言、超时、重试、并行、变量替换、优先级权重、可选条目。可选条目会让「通过」含义变模糊——真可选就不写进验收。

### 4.2 校验规则

服务端 zod 严格模式（多余字段即拒绝），并在 CLI/前端做同一份校验（共享类型）：

1. `items` 至少 1 条；`id` 冲突、`action`/`expect` 为空、`expect` 只写「正常/OK/符合预期」这类不可观察措辞 → 拒绝（后者用固定黑名单短语）。
2. `kind=auto` 的 `action` 必须像命令（含空格或可执行名），且 `expect` 必须含可判定信号（`EXIT=`、HTTP 状态码、数量、`✔/✖`、文件路径变更之一）。
3. `kind=manual` 的 `evidence` 不得为 `none`（人眼判必须留证）。
4. 序列化后 ≤8 KiB。

## 5 展示形态

### 5.1 详情页独立区块（主形态）

- 位置：字段区内，「描述」之后、「标签」之前，标题「如何验收」，右侧显示 `已勾 3/7`。
- 默认展开：状态为 `进行中` / `待验收` 时展开；`待规划` 时收起（写卡阶段点开编辑）；`已关闭` 收起。
- 条目渲染：
  - `auto`：等宽单行命令 + 复制按钮 + 右侧 `expect` 灰字；**不提供「运行」按钮**（看板不获得执行权限）。
  - `manual`：复选框 + `action` 正文 + `expect` 判据；`evidence=screenshot` 显示「需截图」小标，`terminal`/`json` 同理。
  - 前置状态独立置顶，命令同样可复制。
- 勾选：本地辅助态，key 形如 `agentboard.acceptance-ticks:<issueId>:<updated_at>`（卡一更新即失效，杜绝旧勾选残留）；不落库、不共享，UI 上明确写「勾选仅本机自查，不作为验收记录」。
- 「生成验收结论」按钮：把 `3/7` 的勾选结果、未勾条目、证据缺项拼成一段文本，**填入评论草稿**（不自动发送）；验收人补证据后照常走 `kb accept`。

### 5.2 看板卡片标记（轻量）

- 仅 `待验收` 状态显示：有验收清单 → `验收 7 项`；无 → 琥珀小标 `缺验收清单`。
- 不显示 `3/7` 类进度：勾选态是本地的，列表上给共享进度就是假数据。
- 其它状态不显示，避免列表噪音。

### 5.3 自动化与人工并存规则

- 排序固定：`preconditions` → `auto` 条目（按书写顺序）→ `manual` 条目（按书写顺序）。机器能判的先跑，失败就不用浪费人眼。
- 两种条目**共用同一通过口径**：所有 `auto` 项通过 + 所有 `manual` 项通过 = 验收通过；`failIf` 命中任一 = 不通过。不设部分通过。
- 证据归属：`auto` 的证据是终端输出/JSON（贴进评论）；`manual` 是截图（评论附件）。数据库不存证据二进制。

## 6 编辑权与冻结

- **可编辑**：`待规划` 状态，作者与工作区 owner/member 均可改（复用现有 actor 权限，不新增权限位）。
- **冻结**：`kb claim` 成功即只读；`待验收` / `已关闭` / `已废弃` 一律只读。服务端在 PATCH 与 CLI 两层同时拦，不只靠前端禁用。
- **解冻**：两条既有路径，不新增状态：
  1. `kb reopen` 到 `待规划`（整卡重开，语义清晰）；
  2. 携带 `acceptance_change_reason`（≤200 字）的 PATCH / `kb update --acceptance-change-reason`：服务端接受修改，并把原因作为审计评论写入评论流（author 为操作者），验收人能看到「标准在 X 时刻因 Y 被改」。
- 执行 agent 默认不得改：`executing-task` 技能写明「执行中改验收标准视为逃逸，必须走 reopen，或带 reason 并说明」。
- 验收人只能勾选与写结论，不能改条目——避免「判据不合我意就改判据」。

## 7 迁移与录入

### 7.1 单一真源

- 新卡：验收只写 `acceptance` 字段，description **不再**写 `## 验收` 段（模板同步改写）。
- 双写守卫：`acceptance` 非空且 description 仍含 `## 验收` → CLI `kb acceptance lint` 报 `DUPLICATE_ACCEPTANCE_SOURCE`；详情页以字段为准，并把旧段落折叠提示「描述内仍有旧验收段」，不重复展示两遍。

### 7.2 存量迁移（不自动改写）

- 理由：271 张卡的散文验收自动切分必然产出假结构（无命令、无判据、条目边界靠猜），比不迁移更糟。
- 提供 `kb acceptance migrate <id> --dry-run`：读 `## 验收` 段列表项，按规则初判 `kind`（含命令/`EXIT`/HTTP 状态 → `auto`，否则 `manual`），原文填入 `expect`、`action` 留空，输出「待补全清单」；**不加 `--write` 不落库**。首轮只对当前 `待验收`（57 张）跑，人工确认后逐张写入。
- 已完成迁移的卡在知识库/变更日志留一条批量结论，不再逐卡评论。

### 7.3 录入入口

- `kb create-issue --acceptance-stdin`（JSON 或 `- 步骤 | 判据` 的简写行，CLI 归一化成 v1）。
- 智能草稿：模型输出的 `acceptance` 文本**不直接信**，落成 1 条 `manual` 项并把原文放进 `expect`，标 `evidence=screenshot`，留给人补 `action`。
- 新建卡弹窗：可选填 JSON；留空不阻断建卡（阻断会把存量流程一起打挂），由 `lint` 与板卡标记提醒。

## 8 明确不做的部分

1. 不做万能表单 / 条件分支 / 嵌套分组——验收只有「前置 + 条目」两层。
2. 不在看板侧执行命令或跑测试（无沙箱、无权限、无法复现环境）。
3. v1 不建 `acceptance_item` / `acceptance_run` 子表，不做多人共享勾选。
4. 不做验收评分、通过率、看板级验收看板。
5. 不引入「部分通过」「有条件通过」等新状态，状态机保持五态。
6. 不改 `kb accept` 的【验收记录】格式与 `kb close` 语义。
7. 不把截图/日志上传进数据库；证据走评论附件。
8. 不做验收模板继承、跨卡复用、按组织维护标准库。
9. 不要求存量 727 张卡一次性补齐——缺清单只在 `待验收` 期暴露。

## 9 实现拆分建议（本轮不建卡）

| # | 卡 | 内容 | 依赖 |
| --- | --- | --- | --- |
| 1 | 契约与服务端 | `issue.acceptance` 加列迁移（幂等）、shared 类型、zod 严格校验、PATCH 冻结门禁 + `acceptance_change_reason` 审计评论、单测 | 无 |
| 2 | CLI 与 MCP | `create-issue --acceptance-stdin`、`show` 渲染清单、`kb acceptance lint` / `migrate --dry-run`、`update --acceptance-change-reason`、MCP 对应工具 | 1 |
| 3 | 详情区块 | 独立区块渲染、本地勾选、命令复制、生成结论草稿、冻结态提示、可访问性（键盘/aria/reduced-motion） | 1 |
| 4 | 板卡标记 | 待验收卡 `验收 N 项` / `缺验收清单` | 1（可与 3 并行） |
| 5 | 入口与迁移 | 新建卡模板、智能草稿映射、`writing-task` / `executing-task` 技能更新、存量 57 张 dry-run 报告 | 2、3 |
| 6 | 文档与收口 | `Docs/api.md`、知识页回写、三端测试、`docs` 与技能一致性核对 | 2、3、5 |

顺序建议：1 →（2、3、4 并行）→ 5 → 6。P2 备选（仅在出现「多人同时验收同一张卡」的真实需求时立项）：新增 `acceptance_run` 表存勾选与证据引用，JSON 结构原样搬入子表。

## 10 留给实现阶段的决定（不阻塞设计批准）

- 独立区块默认展开阈值（条目 >6 时是否强制收起）。
- `id` 是否允许字母语义（`gate-check`）还是统一 `v1…vN`（倾向后者，减少与验收人沟通成本）。
- 简写行解析的边界（`- 步骤 | 判据` 之外是否支持 `- 步骤 -> 判据`）。
