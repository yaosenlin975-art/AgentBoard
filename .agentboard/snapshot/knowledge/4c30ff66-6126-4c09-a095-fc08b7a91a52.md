# 聊天附件投递：图片走 image 通道，非图片走 prompt 路径

## 契约

- `POST /api/sessions/:id/messages` 收到 `attachment_ids` 后按 DB `kind` 分流：`kind=image` 走 `RunTurnOptions.attachments`（adapter `--image`）；`kind=file` 不占 image 通道。
- 纯文件消息不要求 CLI 图片能力（会话 model 可为空），不会触发 `IMAGE_DELIVERY_UNVERIFIED`。
- 文件本体留在服务端附件存储（`<storageDir>/<uuid>`），prompt 末尾追加「## 随附文件（本轮）」块：文件名、MIME、人类可读体积、绝对路径；agent 需要时自行读取。文件内容不进入消息正文。
- 混合附件只把图片放进 `attachments`；`session_attachment.delivery_state` 对图片与文件统一推进 sending → delivered/unknown。
- 文件下载仍强制 `Content-Disposition: attachment`；落库文件名经 `safeFileName` 去掉路径段与控制字符，存储路径只认 `<storageDir>/<uuid>`，不接受客户端文件名参与路径拼接（防穿越）。

## 前端配合

- 草稿附件状态是 `{id,url,name,mime,bytes}`；正文只物化图片 markdown（`attachmentMarkdown` 过滤 `image/*`），非图片不写正文（否则会渲染成坏图片）。
- 发送闸门不再按类型禁用：所有附件 id 一起提交，由服务端分流。

## 测试套路

- 用 `createApp` + route 级请求 + `FakeAdapter`：文件用例把 session model 设为 null，可直接证明「未走图片能力验证」。
- 断言 prompt 含 storageDir 前缀且不含 `..`；下载响应头以 `attachment` 开头。
