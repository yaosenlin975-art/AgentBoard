# 桌面壳退出语义：附着/自拉两态与 LaunchAgent 托管（B11）

## 口径

托盘「退出」只停「壳自己拉起的 server」（`ServerHandle.child: Some`）。启动时端口已健康（LaunchAgent 开机拉起、手动先起的服务）是附着态（`child: None`），退出只断开不停服、服务 pid 不变、不碰它的 `server.lock`。自拉场景退出停服后，若外部 LaunchAgent 设 `KeepAlive=true`（仓库 `kb autostart` 写的 plist 默认 `KeepAlive=false`），launchd 会按自启语义再拉起——这是配置行为不是拉锯；彻底停服用 `kb autostart uninstall`。

## 两处防拉锯实现

1. **启动宽限（server_process.rs `launchagent_custody` + `ensure_server`）**：`~/Library/LaunchAgents/com.agentboard.server.plist` 存在且端口未健康时，先给 launchd 15s 宽限（KeepAlive 重启有 ~10s 节流）再回落自拉，避免壳抢跑 spawn 与 launchd 争端口/单例锁。plist 检测是纯 fs 判断，`#[cfg(target_os = "macos")]` 分支，Windows 恒 false（行为不变、可编译验证）。
2. **退出等启动收口（main.rs `wait_boot_settled`）**：退出早于 server 健康是真实竞态——`shutdown` 从状态槽里拿不到句柄（还在 `ensure_server` 健康等待里），若直接 `exit(0)`，后台启动线程随进程死亡，刚 spawn 的 node 成孤儿：端口/锁不释放，KeepAlive 场景还会与 launchd 再拉起的实例持续争端口（真正的拉锯种子）。修法：三个退出线程（托盘退出、`--quit-after-ms`、tray 探针）在 `shutdown` 后 `wait_boot_settled`——等启动线程收口再 exit；上限 70s 覆盖 `ensure_server` 的 60s 健康超时。该等待**不能**放进 `RunEvent::Exit` 处理器（事件线程不可阻塞）。

## 判据必须是只增不减的状态（063c0ca5 的教训）

`wait_boot_settled` 早期用 `boot.outcome.is_some()` 当判据，是错的：`start_server` 线程把结果写进 `outcome` 后立刻 `apply_boot`，而 `apply_boot` 用 `take()` 把槽位读走。等退出线程去轮询时槽位恒为 `None`，于是**每次退出都等满 70s 上限**（实测托盘「退出」→ 进程消失 70.16s；用户体感「服务早停了、图标也没了，但壳还在」）。

修法：加一个只增不减的 `boot.settled: AtomicBool`，启动线程在写回结果、跑完 quitting 竞态分支后置位；`wait_boot_settled` 只认它。轮询主体抽成纯函数 `poll_until(deadline, ready) -> bool` 便于单测（真实 `AppHandle` 无法在单测里构造），单测两条：已置位必须 <500ms 返回、永不置位必须按 deadline 超时返回 false。

推论（写新退出路径时照做）：**退出等待的判据不能是被 `take()`/`swap()` 消费掉的槽位**，只能是单调标记位；否则判据失效不会报错，只表现为「退出慢」，很容易被误当成停服耗时。

## Windows 侧验证法

隔离 `APPDATA` + 独立端口（`%APPDATA%\AgentBoard\config.json` 写 `{"port":8899}`）跑 dev 二进制：

- 逻辑覆盖：`--quit-after-ms 3000`（退出早于健康，覆盖竞态分支）与 `--quit-after-ms 15000`（健康后退出，覆盖常规停服）都应 exit 0、端口无监听、`server.lock` 不存在。修复前 3000ms 场景会留下孤儿 node（父进程已退、端口仍监听、锁残留）。
- 真实点击耗时：脚本 `.\logs\tray-audit\measure-exit.ps1`（UIA 找溢出区里无 UIA name 的托盘按钮 → 物理右键 → 点菜单末项 → 250ms 轮询 `Get-Process`），`-Attach` 开关验证附着态。注意 **工作站锁屏时任务栏被 `LockScreenBackstopFrame` 覆盖，合成点击无效**（`WindowFromPoint` 在任务栏坐标返回该类即判锁屏），此时只能改天实测或用逻辑覆盖取证。

实测读数（Windows 11，dev 二进制，隔离 8899）：修复前 70.16s / 用户观测约 71s；修复后 **点击「退出」→ 进程消失 1.17s**，同一次运行里 8899 无监听、无残留 node 子进程、`server.lock` 已删；附着态（先起 8899 服务再启壳）1.31s 退出，外部 server pid 与 `/api/version` 的 pid 均不变、锁不动。
