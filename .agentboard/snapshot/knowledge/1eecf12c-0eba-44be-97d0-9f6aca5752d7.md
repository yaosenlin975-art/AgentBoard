# PERF-4 契约：/api/issues 字段裁剪、分页与 counts 端点

## 结论（待用户确认后实施）

`GET /api/issues` 的传输成本走三条收敛，**缺省行为完全不变**（旧调用方零改动）：

1. **分页沿用已有 `limit` + `offset`**，不新造 cursor。服务端 `pageQuerySchema` 已实现（`limit` 1–100、缺省 50，`offset` ≥0），`listIssuesPage` 也已上线；再引入 cursor 会形成两套分页语义，而 `offset` 对「按状态列翻页」足够。**文档补登记，代码零新增分页分支。**
2. **新增 `fields=` 白名单**：逗号分隔字段名；未传 = 当前完整字段（兼容）。白名单同时决定三件事：SELECT 投影、是否跳过重聚合列（`comment_count` / 依赖聚合 / 决策投影）、是否裁剪 `description`。未知字段名 → 400（列出可用值），避免拼错静默少字段。
3. **新增 `GET /api/issues/counts?workspace_ids=a,b,c`**：按状态聚合计数，替代面板 N+1 全量拉取。`workspace_ids` 必填、去重后上限 50；任一所请求工作区不存在 → 404（与 `requireExistingWorkspace` 同口径）。按「目标库」分组聚合：中心库一条 `GROUP BY workspace_id, status`，已下沉工作区各自一条，不跨库拼 SQL。

回滚开关：服务端环境变量 `AGENTBOARD_ISSUES_V2=off`（或 `0`）——`fields=` 被忽略（返回完整字段）、`/api/issues/counts` 返回 404 `NOT_FOUND`；客户端遇到 404/400 时回落旧全量路径。默认（未设置/其它值）走新分支。

## 端点契约

### GET /api/issues

| 参数 | 说明 |
| --- | --- |
| `workspace` / `workspace_id` | 必填，二者等价（既有口径） |
| `status` | 可选，按该工作区字典校验（既有口径） |
| `limit` / `offset` | 可选；任一存在即走分页，返回 `PageResult<TaskPreview>`（既有口径） |
| `fields` | 可选，白名单。给出时只返回所列字段，并跳过未被请求的重聚合列 |

可选字段名（与 `Issue` 同名）：`id, workspace_id, title, description, priority, labels, status, sort_order, parent_issue_id, claimed_by, claimed_at, session_id, due_date, due_time, comment_count, blocked_by_count, blocked_by_open_count, resolved, dependency_violation, decision_locked, open_decision_id, decision_grace_until, decision_waiting_seconds, created_at, updated_at`。

- `description` 不在白名单 = 不查/不传正文，响应**不带** `description_truncated` / `next_description_offset_chars`。
- `comment_count` / `blocked_by_*` / `resolved` / `dependency_violation` / `decision_*` 不在白名单 = 跳过对应子查询与 JOIN。
- 分页仍按 `i.id ASC`（既有 `listIssuesPage` 排序），`next_offset` 语义不变。

### GET /api/issues/counts

请求：`GET /api/issues/counts?workspace_ids=<id,id,...>`（逗号分隔；也接受重复参数 `workspace_ids=a&workspace_ids=b`）。

响应：

```json
{ "items": [ { "workspace_id": "…", "total": 648, "counts": { "待规划": 32, "进行中": 4, "待验收": 9, "已关闭": 600, "已废弃": 3 } } ] }
```

- `counts` 是状态名到数量的映射，只含实际有卡的键；客户端用自己的状态字典补 0，「字典外状态」继续由客户端归入「其他」，统计加总恒等于 `total`。
- 未知状态名不报错（自定义状态照常返回），不做字典校验。
- 缺参/空串 → 400；去重后 >50 个 → 400；工作区不存在 → 404。

## 实测基线（2026-11-07 本机 8787，本工作区）

- `GET /api/issues?workspace=…` 全量：`size_download` **1,529,586 B**，`time_total` 1.33 s / 1.84 s。
- `GET /api/issues?workspace=…&limit=50`：`size_download` **110,567 B**，`time_total` 0.317 / 0.458 / 0.392 s。
- 结论：分页已把 p50 压到 500 ms 内，但 payload 仍超 100 KB；**必须叠加 `fields=` 才能达标**（去掉 `description` 与重聚合列）。counts 是单表 `GROUP BY`，不涉及逐行子查询，预期远低于 50 ms。

## 迁移与回滚

| 调用点 | 现状 | 迁移 |
| --- | --- | --- |
| Web `WorkspaceCard.tsx:97-100` | 每张工作区卡各发一次全量 `GET /api/issues`（N+1） | 由列表容器一次 `GET /api/issues/counts?workspace_ids=<可见工作区>`，把计数下发给卡片；counts 404/失败回落旧全量查询 |
| CLI `listTasks.ts:253-256` | 平铺列表整区全量；`--tree` 整区全量 | 非 `--json --full` 时加 `fields=`（保留现有输出所需字段），400/404 回落全量；`--json --full` 仍取完整正文 |
| MCP `apps/mcp/src/tools/tasks.ts:102-103` | 已用 `limit/offset` | 加 `fields=` 投影，语义不变 |

回滚：设 `AGENTBOARD_ISSUES_V2=off` 重启服务即可让新分支失效；客户端代码保留回落分支，不需要一起回滚。

## 验收映射

1. `limit=50&fields=<白名单>` 三次取样 p50 ≤500 ms、payload ≤100 KB（命令见证据，附改前/改后）。
2. counts 与全量聚合逐工作区抽样 3 个一致（脚本比对，附命令与输出）。
3. 切换面板网络记录：不再出现每卡一次全量 `/api/issues`；改为 1 次 counts。
4. `Docs/api.md` 登记两个端点与回滚开关；`pnpm -r build` + 相关测试通过。
5. 真实 `createApp` 断言 `/api/issues/counts` 非 404、`fields=` 生效、缺省响应与旧版逐字段一致。

## 客户端落地：Web（PERF-4b，2026-11-07）

- 工作区抽屉（`WorkspaceList`）用一条 `useQuery(['issues','counts',visibleIds])` 拉 `GET /api/issues/counts`，按 visible 工作区拼 `workspace_ids`；服务端单次上限 50，超出按 50 分批循环合并。
- `WorkspaceCard` 新增 `statusCounts` 三态：`undefined`＝加载中（先按 0 渲染，**不发**全量请求）、`null`＝counts 失败（才启用旧 `GET /api/issues` 回落）、对象＝直接按字典映射并把字典外状态归「其他」。
- counts 查询 `retry: false`：旧服务端 404 时立刻回落，不会重试 3 次拖慢界面。
- 陷阱：counts 的 queryKey 用 `['issues','counts',ids]` 前缀，能吃到现有 `invalidateQueries({queryKey:['issues']})`；但只失效 `['issues', workspaceId]` 的路径不会刷新 counts，靠抽屉重新打开时的 staleTime=0 重取。
- 验证：`WorkspaceList` 三个用例（1 次 counts、无全量请求；字典外归其他且加总=total；404 回落）。测试页 5174 实测 7 个工作区只发 1 次 counts。

## 客户端落地：CLI（PERF-4c，2026-11-07）

- `kb list-tasks` 默认向 `GET /api/issues?…&fields=` 传白名单（`packages/cli/src/commands/listTasks.ts` 的 `LIST_TASK_FIELDS`），**不含 `description`**：表格本就不输出正文，`--json` 非 `--full` 也会由 `projectForJson` 摘除；只有 `--json --full` 走无 `fields` 的全量请求。
- 白名单顺序刻意与 `rowToIssue` 的键序一致（去掉 `description`），因此 `--json` 逐行输出不变（实测键序一致、除 `description` 外深比较相等）。
- 回落：服务端不认 `fields=`（400 校验错或 404 路由缺失）时静默改发全量请求，进程内只回落一次；其它错误照常抛出。
- 实测（8787，660 条）：API 回包 1,547,807 B → 462,661 B；`kb list-tasks --json` 650,735 B，`--json --full` 1,718,061 B。
- 改测试时注意：单测 mock 的 `/api/issues?workspace=…` 精确匹配要改成 `startsWith`，否则会命中回落分支而不是 `fields` 分支。

## 客户端落地：MCP（PERF-4d，2026-11-07，用户拍板选项 A）

- **口径变更（用户 2026-11-07 拍板，选项 A）**：允许 MCP `list_tasks` 不再输出 `description`，正文改由 `get_task` 提供；原「输出字段与改前一致」的验收作废。这是有意的契约变更，不是静默丢字段。
- 实现（`apps/mcp/src/tools/tasks.ts`）：平铺列表向 `GET /api/issues` 传 `fields=`（`LIST_TASK_FIELDS`，与 CLI 同序、不含 `description`）；树端点 `/api/issues/tree` 没有 `fields=`，在 MCP 侧用 `omitTaskDescription` 统一剔除 `description` / `description_truncated` / `next_description_offset_chars`。
- 回落：服务端不认 `fields=`（400 `VALIDATION_ERROR` 或 404）时，进程内一次性回落全量请求，回落结果同样剔除正文——旧服务端不会让列表突然又带正文。
- 不悄悄降级：`list_tasks` 与 `get_task` 的 tool description 都明说「列表不含正文、要看正文请用 get_task」，`tools/list` 可见；基本不影响 schema 入参。
- 用例（`apps/mcp/test/tasks.test.ts`）：平铺列表请求带 `fields=` 且白名单不含 `description`；列表出参无正文三键、`get_task` 同一任务仍有正文（对偶断言）；树列表同样剔除正文；400 回落只发两次请求且出参仍无正文。
- 真机取证：真实 `apps/mcp/dist/index.js`（stdio）+ 8787 真实库，`list_tasks` 出参 26 键、无 `description`；同卡 `get_task` 返回 426 字符正文。
