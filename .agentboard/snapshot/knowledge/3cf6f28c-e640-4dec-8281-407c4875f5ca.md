# 看板批量改状态：并发上限 6 + 部分失败收敛（CR-4）

## 契约

- `Board.tsx` 的 `applyBatchStatus`：选中的 N 张卡按并发上限 **6**（模块级 `BATCH_PATCH_CONCURRENCY`）逐张 PATCH `/api/issues/:id`，不再 `Promise.all` 全并发。上限可调常量，单测断言实际并发 ≤ 6。
- 并发执行用 `apps/web/src/lib/promisePool.ts` 的 `mapWithConcurrency(items, limit, worker)`：固定 lane 数从队列取任务，单任务失败不中断其余任务，结果按输入顺序返回 `PromiseSettledResult[]`（Promise.allSettled 语义）。后续其它「逐条写请求批量打」场景直接复用，不要再各写一套。
- 无论成败统一执行一次 `invalidateQueries(['issues', workspaceId])`：已成功写入的卡立刻反映到界面，不依赖 WS 帧自愈。
- 部分失败收敛：失败 id 保留在 `selectedIds`（成功卡从选择集中剔除，重试只重打失败卡，不重复 PATCH 已成功卡）；错误横幅逐条列原因，格式「批量移动完成：成功 X 张，失败 Y 张 —— <标题>：<err.message>；…」。
- 失败原因取 `ApiError.message`（服务端 `{ error: { code, message } }` 的 message），409 占用、TIMEOUT、网络错误都按此路径进横幅。

## 测试口径

- `src/test/boardDisplaySelection.test.tsx` 新增 describe「批量改状态：并发上限与部分失败收敛（CR-4）」两条：
  - 第 3 张卡 mock 409：断言 5 张全部被尝试、其余 4 张落库、失败卡保留选中（已选 1 / 5）、横幅含原因、`GET /api/issues` 至少被拉取 2 次（invalidate 生效）。
  - 20 张卡批量：PATCH handler 内计数 in-flight，断言峰值 ≤ 6 且 20 张全部落库、成功后选择清空。

## 边界

- 批量仍是逐张 PATCH，服务端契约不变，无新增端点。
- `noUncheckedIndexedAccess` 下 `items[index]` 是 `T | undefined`，池实现里取队列项需 `items[index]!`（lane 存活条件已保证不越界）。
- 该测试文件跑批时 MSW 会告警 `GET /api/workspaces/:id/statuses` 未注册 handler：属既有现象（该文件从不 mock statuses，`useWorkspaceStatuses` 失败回落内置五列），非本卡引入。
