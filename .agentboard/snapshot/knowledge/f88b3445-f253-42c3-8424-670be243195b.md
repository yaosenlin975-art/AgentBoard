# AgentBoard 测试与门禁

## 门禁顺序

1. `pnpm -r build`（**tsc 兜底**：vitest 不做类型检查，全量测试绿仍可能漏 TS 错误；必须在所有文件落地之后跑，先跑后写会让结论失效）。
2. `pnpm --filter @agentboard/web test` / `--filter @agentboard/server test`（server 满载时可用 `--no-file-parallelism`）。
3. 界面行为：测试页 5174 真机（CDP），不要用「我重建了 dist」冒充验证。
4. 正式页：`pnpm publish:web`；产物新鲜度看 CSS/JS 里的**新增标记**（重建后哈希可能不变，别只比文件名）。

## 变异 RED（回归验证的必要条件）

- 每个修复要能证明「去掉修复会失败」：改回旧行为跑一次，断言变红，再还原。
- 只在「新增断言」没有对应行为变化时才允许标注「仅新增覆盖」。

## 并发与 flake 口径（判缺陷前先单跑）

- `knowledge.test.tsx` 是长期允许项；`detail.test.tsx` 的 DispatchDialog、`knowledgeGraph` 300 节点、`gitOnDone`/`gitBaseline` 在满载时超时，**单跑即绿的不算回归**。
- 满载下 `codebuddy`/`codex` 有 429 额度限制，`IMAGE_DELIVERY_UNVERIFIED` 400 属外部条件，不是实现缺陷。
- 判定基线要写进卡评论，避免下一批复审重复争论。

## GIT-ON-DONE

- `kb done --scope` **必须逐条传参**（`--scope a --scope b`）。逗号串会被 PowerShell 拆坏，导致 scope 变成不匹配值、自动提交零命中；服务端现在会打 ⚠ 系统评论并给可复制补救命令，但仍要按逐条传。
- 声明了 scope 却零命中 → 提交不会发生；先用评论里的补救命令手工提交，再修卡。

## 其他硬门禁

- `apps/web` 的 `pretest` 会跑 BOM 检查（`scripts/check-bom.mjs`）：**不要用 PowerShell 5.1 的 `Set-Content -Encoding UTF8` 写仓库文件**（会带 BOM，把 Vite/JSON 打挂）；用 write 工具或 `utf8NoBOM`。
- 环境变量/配置的非法值要**装配期 fail-fast**（例如未知 region → 400 `CHECKIN_REGION_UNSUPPORTED` 且不发任何 HTTP），不要静默回落默认值。
- 装配期 fail-fast 不能被「懒解析」架空（ACC-KB-A1）：把 origin 解析留在请求闭包（`workbuddyBillingUrl(region, ...)` 只在首次请求里调用）时，构造期不会抛，`region=unknown` 要拖到第一次 HTTP 才报错。恢复口径：构造时先 `workbuddyBillingOrigin(config.region)` 解析一次；证明用变异 RED——删掉该行后 `apps/server/test/workbuddyHosts.test.ts` 的装配期用例必须转红。
- 迁移演练一律用**隔离 APPDATA + 独立端口**，不要拿 8787 的真实库做实验。

## 基线判定与并发 flake（原 project-status-2026-11-03 结论）

- 空闲基线（2026-11-03 07:2x 实测）：server 47 files / 440 tests 全通过；web 39 files / 383 tests / 382 passed（唯一失败 `knowledge.test.tsx:66`）；`pnpm -r build` exit 0。
- **并发跑测试会 flaky**：`gitOnDone.test.ts` 与 `imageDelivery.test.ts` 在 Windows 上删临时目录报 EPERM 并超时（全量并发 349s、出现 4–7 条失败；单独跑 33 tests 全过、17.7s）。判断基线必须**空闲状态重跑**，不要据并发结果下结论。
- 基线数字要写进卡评论，下一批复审直接复用，不重复争论。

## 「无新增失败」判定流程（原 B4W 结论）

1. 用 `--reporter=json --outputFile=<path>` 拿**失败文件清单**（文本输出会被截断，看不全）。
2. 逐条核对失败文件是否 import 了本次改动的模块；**无交集即零影响面**。
3. 引用了本次改动模块的测试文件必须**全部通过**（例：accounts 相关 15 个文件全绿）。
4. 该判定只支持「本卡未引入新失败」，不等于全仓绿。

## 变异 RED 实例口径（原 CHAT-RENDER01 / UI-FILTER01 结论）

- 前端渲染类：把样式类（`rounded-lg`/`bg-*`/`border`）加回本应无壳的容器，对应 2 条断言必须转红。
- 状态/钩子类：把 `useMemo` 挪回提前 `return` 之后（hook 数量随分支变化）可复现 `Rendered more hooks than during the previous render` 的 RED。
- 骨架编排类：去掉 `start` 失败 → 回滚的分发分支，流程级用例必须转红。

## 隔离实例演练的正确姿势（KB-TECH-01 / 73b43d44）

- **子进程必须继承完整 env**：最小 env 启动会让 provider 初始化抛 `ApiError: 无法解析本机 WorkBuddy 契约路径` → 进程 **exit 1、端口从未监听** → 客户端只看到 `ECONNREFUSED`。此时任何「代理 / 端口占用 / 权限」方向都是误判。
- 诊断顺序：先看子进程退出码与 stderr（有没有 ApiError），再看端口是否曾被监听；不要先查代理。
- `.logs/server.log` 按 **cwd** 共享：同一 cwd 下多个演练实例写同一文件，日志里的 `listening on …` 可能来自别的 pid —— **诊断必须按 pid 过滤**，否则会把「别的实例在监听」当成「本实例启动成功」。
- 演练前清 `server.lock` 与 `db-migration-status-*.json`：上一轮残留会让新实例走复用/接管分支，结果不可信。
- 隔离实例用独立 `AGENTBOARD_DB` 与独立端口，否则写进真实库。

## Node 24 代理门禁（KB-TECH-01 / c1eab19c）

- 起服务的脚本必须注入 `NODE_USE_ENV_PROXY=1`（Node 24 默认不读代理变量），`NO_PROXY` 必含 `127.0.0.1`。
- 断言写法：用 `http://user:secret@…` 作代理，断言响应只回 `127.0.0.1:7897` 且整串不含 `secret` / `user`（防凭据回显）。
- 共享侧 `packages/shared/test/proxyEnv.test.ts` 覆盖 6 例（注入 / 缺省 / `=0` 关闭 / NO_PROXY 回环）。
