# 账号三链路真机验证结论与坑(2026-11-06 闲时复核)

## 三链路真机基线

- **Trae(获取→签到全通)**:正道是 `POST /api/managed-accounts/trae/capture-current`(DesktopProvider 读 `%APPDATA%\Trae CN\User\globalStorage\storage.json`),捕获即建行+回填签到凭据(has_checkin_credential=true);随后 POST /api/checkin-runs 真实签到成功(2026-11-06 实测,账号 last_checkin_day 当日 succeeded)。**python 内存扫描对 Trae CN 无效**(跑满 134s 也是 0 结果),不要再用 import-credentials 的 trae 平台当获取入口。
- **WorkBuddy(进程强依赖)**:capture-current 需要 WorkBuddy.exe 运行,未跑时 409 CLIENT_NOT_RUNNING(行为正确);插件线明文 JWT(Tencent-Cloud.coding-copilot.info)的回填挂在桌面捕获内部,进程不在整链挡死(ACC-FIX-4 处理)。
- **MiniMax(token 易过期)**:auth.json 的 accessToken 形态是 60 字符 `mmo` 开头的裸串(非 JWT);过期后平台 401 `invalid access token`;同记录带 refreshToken 但导入/签到链路均未使用(ACC-FIX-3 处理)。device grant 换 token 端点 `origin + /oauth2/token` 在 addAccountProvider.ts 已存证。
- **添加账号协议骨架可用**:五协议清单/设备码会话创建/轮询/取消全部真实可用(account.minimax.cn 真实签发 user_code);最后一步 requires_browser 需人工浏览器授权,无人值守环境约束。

## 坑 1(ACC-FIX-1 已修):SAFE_ERROR_CODES 漏登记=错误码被吞

httpCheckinProviders 对平台 401/403 抛 `ApiError(409,'CHECKIN_CREDENTIAL_INVALID')`,但 operationRunner.ts 的 SAFE_ERROR_CODES 集合漏登记该码,`operationRunner.ts:49` 把它归类为 ACCOUNT_OPERATION_FAILED——真实原因(凭据失效)到不了 batch item 与 UI,「重新导入凭据」指引永不触发。真机表现:minimax 过期凭据签到只显示裸失败。

**规则:新增任何 ApiError 业务码并期望落库/UI 可见时,必须同步登记进 operationRunner 的 SAFE_ERROR_CODES,并在 grep CHECKIN_CREDENTIAL_INVALID 一类的既有码清单里核对消费方(web 端码文案映射)。**

## 坑 2(ACC-FIX-2 修):导出扫描 20s 必超时且无原因

credentialImport.ts DEFAULT_TIMEOUT_MS=20000,而 trae 内存扫描实测 134s——服务端必超时,响应只给 EXPORT_FAILED 无原因,server.log 也不留 [export-credentials] 痕迹(audit console.log 不落日志文件)。workbuddy 扫描 5s 内正常(进程未跑时 found=0)。真机排障时先怀疑超时,再怀疑平台。

## 验证套路(真机取证链)

1. `GET /api/managed-accounts` 看目标账号 `has_checkin_credential` / `client_instance_id`(imported=minimax 文件线,trae-desktop=捕获线,minimax-desktop=桌面捕获线)。
2. `POST /api/checkin-runs`(带 Idempotency-Key 头,body `{app_id, account_ids:[<managed 账号 UUID>]}`)→ 202 → `GET /api/checkin-runs/<batchId>` 轮询 items[].state/safe_error_code。
3. item 失败时拿 operation_id 查 `GET /api/account-operations/<id>` 看 stage(preflight=queryStatus 阶段)与 safe_error_code。
4. 凭据有效性判定(不落明文):用 SecretVault.unprotect 同 scope 解出后直接 fetch 平台 status 端点看 401/200——不要打印 token 本体。

## 追加(2026-11-06,GitHub 同类实现调研):三痛点的可借鉴模式

调研范围:refresh token 续期 / 签到自动化 / 多账号凭据管理 三主题,各 2-3 个代表仓库,结论全部来自源码实读(gh 未登录,走公共 API+浅克隆,已清理)。

### refresh token 续期(ACC-FIX-3 直接参考)

- **zhanghaojie513/waygate-mmcode**(MIT,2★):MiniMax Code 官方设备授权本地反代,`src/credential.ts` 是完整 MiniMax OAuth 实现——端点 `account.minimax.cn/oauth2/device/code` 与 `/oauth2/token`,client_id=`mcode-public`、scope=`agent.default`、audience=`agent-backend`,PKCE S256 强制。MinimaxTokenManager(credential.ts:370-449):过期前 120s 余量;inFlight Promise 去重做进程内并发锁;**refresh token 一次性且每次刷新轮换,新值必须写回**;刷新被拒抛带 HTTP 状态+响应体前 200 字符+「可能被该账号另一处登录顶掉」的可行动文案。
- **F0Rextasy/minimaxcode2api**(MIT,1★):single-flight Map<refreshToken,Promise> + **spent-token 环形 Set(上限 40)——发刷新请求前先 markSpent,同一 token 二次刷新直接拒**(防重试烧掉一次性 token);mtime 守卫缓存:跨进程协作靠 statSync mtime 变化自动重读 token 文件;401 只做一次 refresh-and-retry。
- google-gemini/gemini-cli(Apache-2.0):refresh 委托 google-auth-library,`on('tokens')` 事件把轮换后的 token 持久化——「刷新与落盘解耦成事件」的模式;协议栈不可移植。
- **关键运营情报(两家源码注释实测一致):MiniMax refresh token 一次性;同一账号只允许一个有效会话,与官方客户端互踢 → AgentBoard 的 minimax 账号应专用;Qoder 支持多会话并存。真机刷新验收需用户在场。**

### 签到自动化

- **Sitoi/dailycheckin**(MIT,8.7k★):每站点返回人类可读 msg 而非抛异常,四态全覆盖(成功带业务数据/已签到/失败带上游 message/异常);账号级 try/except 隔离,单账号挂不影响批次;无重试,幂等靠业务码判「已签到」。
- amclubs/am-check-in(Apache-2.0):`ret!==1&&ret!==0` 双码宽容(0=已签到,1=成功都算过);失败也推送不静默。单文件 322 行,适合当签到模块骨架。
- 对 AgentBoard 的印证:ACC-FIX-1 的错误透传方向与两家一致——失败永远带上游原始码,不吞。

### 多账号凭据管理

- AzureAD/msal-node-extensions(MIT):整 cache 文件一把 DPAPI 锁+账号在 cache 内按 home_account_id 区分(非每账号独立加密);CrossPlatformLock=排他创建 .lockfile 写 pid,500×100ms 退避——比 mtime 守卫更强的跨进程锁。
- gemini-cli:Keychain 优先、失败降级加密文件;按服务名+条目名「命名即隔离」。
- primno/dpapi(MIT):预编译 DPAPI 原生模块,免 node-gyp。
- **所有调研仓库都不做内存扫描**——读取已登录客户端凭据没有开源先例,各家都是自己走 OAuth 拿 token 自己存;痛点方向应是逐步用设备码登录替代内存扫描,而非优化扫描。

### 结论

1. ACC-FIX-3 实现应抄:minimaxcode2api 的 single-flight+spent-ring(防一次性 token 烧两次),端点参数抄 waygate-mmcode,120s 余量+轮换写回。
2. 无先例可抄的内存扫描:长期用设备码登录替代。
3. 错误透传(ACC-FIX-1 已修)是社区共识做法。
未验证:两低星仓库的端点行为是作者实测结论,AgentBoard 落地前需自行复测。
