## 切换（ACC-SW-MAX，2026-11-07 真机实证补充）

minimax 桌面切换已落地（commit 38a4ab8，卡 8b120daa）：start 装配（spawn detached）+ refresh_token 同写 + 能力表/gate 按探测置 true。真机单活跃账号 capture+switch 同号切换 succeeded。追加实证坑：

1. **verify 不能启动后立即读**：客户端启动会归一化重写 `auth.json`（字节变、token 一般不变）。启动后立即读会读到中间态；回滚写盘再与客户端启动写盘**竞态**，会把登录态重置 `auth-state.json: status=anonymous`。修复：verify 在窗口内轮询（默认 20s）到目标 token 才算落地；回滚前必须先 `stop` 客户端。
2. **signin/status 探针必须带 `timezone_id`**：不带时服务端恒回 HTTP 200 + `base_resp.status_code=1406010011`（invalid timezone_id），有效凭据也拿不到结果。带 `timezone_id=Asia/Shanghai`（query 参数）后：有效凭据 200/ok，无效凭据 HTTP 401。该响应**不含任何身份字段**（只有 scene/days），uid 只能走 ACC-FIX-6 同链兜底：JWT sub → 响应字段 → `sha256(token).hex[:16]`。200 但 `base_resp.status_code != 0` 也要按服务端拒认处理。
3. **客户端会自轮换 access_token**：客户端启动/使用会刷新 token 并使 vault 里捕获的凭据服务端失效（401）。capture 与 switch 间隔一久（中间客户端跑过），切换必然在 S5 被服务端拒认 → 安全回滚（回滚后 auth.json 字节级一致）。待办：switch 前用本机快照/refresh_token 自愈凭据，再做切换。
4. **records 键不可从凭据推导**：真实键形 `com.minimax.mcode.oauth.prod.cn\x00<43字符摘要>`；sha256(accessToken/refreshToken/clientId/uid/generation) 全不匹配摘要。实现：优先复用目标账号被捕获快照里的记录键并收敛为单条记录；快照缺失沿用源键（假设单记录原地覆盖不产生并存键）。跨账号互切客户端实际读哪条仍未双号验证。
5. 真机单号验证口径：capture-current → 立即 switchAccount(同号) → succeeded（终态 verify）；能力表 `switch:true / switch_reason_code:OK` 由真探测推导（gate 与能力矩阵同口径，accountRoutes requireProvider 改异步带探测）。

## 切换（ACC-SW-TRAE，2026-11-07 真机实证补充）

trae 桌面切换已落地（卡 c80c0f6c）：`TraeDesktopProvider.switchAccount` 走 switchFlow 七步；15 条目录级快照在 `traeSnapshot.ts`——备份目录 `<db 目录>/trae-snapshots/<ref>/` 镜像相对路径，manifest（逐文件 sha256）走 `vault.protect` 存单条 ref（目录名=同一 ref），还原按哈希值校验；必清 `logs/`（明文 JWT）、`code.lock`、live 的 `state.vscdb-wal/-shm/-journal`。追加实证坑：

1. **客户端在跑时捕获拿不到 webview 登录态**：Chromium 独占持有 `Local Storage/leveldb`、`Session Storage`、`Network`、`Partitions/*` 里的文件，逐目录读失败（EBUSY），快照这几条整段 failed。实现：快照有 failed 条目就自动**停机冷快照升级**（stop → 重拍 → 把客户端拉回来），KB 范式 A 的 S0 不能省。
2. **Partitions 别整目录搬**：`trae-webview` 505MB + `icube-web-crawler*` 309MB 里 Cache/Code Cache/GPUCache 占 ~98%（零账号身份）。快照按分区内子路径跳过缓存目录，单份 ~15MB / 226 文件（真机实测）。
3. **`Stop-Process -ErrorAction SilentlyContinue` 不等于退出码 0**：目标 PID 在列出与执行之间消失（Electron 主进程被杀后子进程自退，Trae 实测 36 进程），`$?` 仍 false → powershell.exe 退出 1 → `clientProcess.stop` 误报探测失败。修复：停止脚本结尾 `exit 0`，「没杀干净」由随后的 isRunning 轮询以 `CLIENT_STOP_TIMEOUT` 暴露；`CLIENT_STOP_TIMEOUT` 同时补进 operationRunner SAFE 码（此前缺登会被吞成 `ACCOUNT_OPERATION_FAILED`，minimax 同链受益）。
4. **exe 装非默认盘**（本机 `D:\Program Files\Trae CN\Trae CN.exe`）：静态候选位全落空，切换前用运行中进程表探测兜底；`AGENTBOARD_TRAE_EXE` 可显式指定。
5. 真机单号验证口径：capture-current（冷快照 226 文件，客户端停后拉回 17 进程）→ switch 同号 → stop→write→verify→**succeeded**；切换后 `is_current:true`、Trae 重启 17 进程、S2 回滚备份成功后已清。能力表 `switch:true / OK` 按 storage.json 存在推导（registry `traeAvailable` 参数可测）。双号互切待用户配合（本机单活跃账号，同号幂等切换为证据口径）。

五平台余额/积分已接线（卡 881b63fe）：`fetchPlatform` 五分支「凭据→端点→解析」全通，端点与鉴权依公共知识 `3c21b76c` §1 矩阵。追加实证与实现口径：

1. **minimax 签名头非必需（推翻矩阵页原口径）**：`POST …/commerce/get_membership_info` 仅 `Bearer <mmoat_ token>` 即 HTTP 200 + `base_resp.status_code=0`（2026-11-07 本机实测，`yy`/`x-timestamp`/`x-signature` 全不带）。矩阵页该行已同步修订。真积分只认 `op_credit_summary.total_remaining_amount`（字符串数字）；`opcredit_balance`/`total_remains_credit` 是已购积分取整，不消费。
2. **凭据解析在 fetch 时做**（`platformQuotaCredentials.resolvePlatformQuotaCredential`，accountRoutes 的 `createQuotaService` 装配处注入 `platformCredential`）：中心库 `managed_account` 签到凭据（vault purpose=`checkin`），同平台多账号取 `updated_at` 最新 enabled；workbuddy 额度来源的账号落在 `workbuddy_desktop`。zcode 走本机 `~/.zcode/v2/credentials.json`（缺失才回落库内 `zcode` 账号）。
3. **zcode 凭据值是 enc:v1 AES-256-GCM**：格式 `enc:v1:<iv b64url>.<tag b64url>.<ciphertext b64url>`，key=sha256(env `ZCODE_CREDENTIAL_SECRET` 或 `zcode-credential-fallback:<platform>:<homedir>:<username>`)（对齐 ZCode CLI 的 createZCodeCredentialCipher）；只认 `oauth:bigmodel:access_token` 键（`zcodejwttoken` 打 quota/limit 必 401，矩阵 §2 已验证）。

5. 失败分支 reason_code 口径：无凭据 `NO_CREDENTIAL`（逐平台可行动指引）；vault 解不开/凭据空 `CREDENTIAL_UNAVAILABLE`；对方 401/403 `CREDENTIAL_INVALID`。qoder_cn 本机无账号即 `NO_CREDENTIAL`——主通道是 openapi Bearer（dt- 桌面令牌），`big_model_credits` 的 Cookie 通道未实现也不需要。

## 列表 is_current 与身份哈希两套派生源（ACC-CUR-FIX，2026-11-07）

1. **identity_hash 有两套派生源，互不相等**：登录态派生 = sha256(app_id + NUL + auth.json 记录键)（captureCurrent 与 getCurrentIdentityHash 同口径）；protocol/imported 线建号派生 = sha256(app_id + NUL + uid)，uid 走 ACC-FIX-6 链（JWT sub → 服务端探测 → sha256(token) 截 16 兜底）。GET /managed-accounts 的 is_current 按登录态派生比对，protocol 线账号切过去后全行 false 是派生不同源所致，不是切换失败。
2. **auth.json 记录键建号时不可预知**：键尾 43 字符摘要无法从凭据推导，要等客户端归一化 auth.json 后才存在 → protocol 行身份只能「切换 verify 通过后回填」（minimaxDesktopProvider.convergeIdentityHashToLoginState），不能在建号时统一。
3. **vault 的 DPAPI entropy 绑完整 scope（含 identity_hash）**：改行 identity_hash 必须先把行上 vault 引用（checkin_credential_ref / client_snapshot_ref）按新 scope 重护再改哈希，旧密文事务提交后才删；checkin/refresh/restore 都按行现值现取 scope，重护后天然兼容。
4. **收敛的护栏**：UNIQUE(app_id,client_instance_id,identity_hash) 被他行占用 → 跳过；捕获线行哈希本就是登录态派生 → 天然 no-op；收敛全程吞错，失败不影响已成功的切换。已知取舍：收敛后同账号再走 protocol 加号线会因 findManagedAccountByAppIdentity(app+hash) miss 建重复行——该去重对 minimax 本就随 token 轮换失效，非收敛引入。
