# 桌面壳端口读 config.json（CR-6）

## 契约

- 壳启动时 `server_process::resolve_port()` 读 `%APPDATA%\AgentBoard\config.json`（`config_dir()` 与 server 端同口径）的 `port` 字段，**读一次、存进 ShellState.port**；探活（is_healthy）、导航（base_url）、重建窗口、停服等端口释放等待全部用它，不再硬编码 8787。
- 解析口径与 server 端 `config.ts` 的 `mergeValidFields` 一致：JSON 数字、整数且 >0；壳侧上界取 u16（`SocketAddr` 解析所需，也是 server 实际可监听范围）。文件缺失 / JSON 损坏 / port 缺失或非法 → 一律退回 `DEFAULT_PORT = 8787`。
- `base_url(port)` / `is_healthy(timeout, port)` / `ensure_server(port)` 改为接收入参；`ServerHandle` 携带本次端口供 stop 后等端口释放。
- 解析纯函数 `parse_config_port(&str) -> Option<u16>` 与 IO 分离，单测直接喂 JSON 串，不碰 %APPDATA%（避免测试改进程级环境变量的并行竞态）。

## 边界与已知限制

- server 端 `AGENTBOARD_PORT` 环境变量可临时覆盖端口；壳侧不读该变量（卡面口径只读 config.json）。用 env 起的非 8787 server，壳探活仍按 config.json 的端口 → 属已知不覆盖项。
- `capabilities/decision-notifications.json` 的 urls 仍固定 `http://127.0.0.1:8787`：Tauri capability 是静态清单，端口改了之后通知权限不会覆盖新 origin（DEC-7 通知在该端口下静默失效），后续如需支持需另立卡（capability 无法按动态端口授权）。

## 人工验收步骤（真机核验由父代理执行）

1. 设置页把端口改成 8790（写入 %APPDATA%\AgentBoard\config.json）→ 启动桌面壳：判定 = 壳健康探活打 8790，窗口导航到 http://127.0.0.1:8790，托盘退出后 8790 释放。
2. 把 config.json 改名/写坏（如 `{ port: "abc" }`）→ 启动壳：判定 = 8787 探活/导航正常（退回默认）。
