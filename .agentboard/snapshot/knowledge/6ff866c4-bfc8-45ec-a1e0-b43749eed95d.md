## 已知过期点（2026-11-07 二次核对，SKILL-DRIFT-2 修正）

| 旧表述 | 现状（权威源 + 实测） |
| --- | --- |

| `--json` 失败仍是纯文本 stderr、不带错误码 | 失败体是 stdout 的 `{"error":{"code","message","details"}}`，退出码不变；分支以退出码为主、`error.code` 为辅（实测 `kb show 0000… --json` → `NOT_FOUND`，exit 1）。 |

## 核对方法

1. **命令存在性**只看 `kb <cmd> --help` 的用法与「退出码」段，不要凭旧帮助文案或对话记忆判断命令是否存在。
2. **必填参数与默认值**以 using-agentboard 的「写知识页」参数段 + 命令 help 为准：`create` 缺 `--domain` 400，`--category` 缺省 `open`。
3. **收尾条件**要交叉核对 using-agentboard 的 CLOSE-RECORD 与 RULE-3 是否在执行类技能（executing-task / handoff / swing-dev）里被完整转述，而不是只写了「能 done」。
4. 找到一处旧表述后，用同一关键句 grep 全部技能副本——同一说法常被复制到 3–5 处，只改一处会留下互相矛盾的文档。
5. **卡面/他人结论不能直接当口径**：2026-11-07 实测发现 SKILL-DRIFT-2 卡面「退出码 3 仅 kb dep 专用」不成立——`decision.ts` 的 `fail3` 也让 ask 族参数错误 exit 3。凡涉及退出码、默认值、选项存在性的断言，至少满足其一才写进技能：`kb <cmd> --help` 原文、源码行号、可复现命令 + 退出码。

## 结论

技能文档里的 CLI 口径漂移不是「谁记错了」，而是**权威源分散**：命令行为在 `kb --help`，参数约束在 using-agentboard 的参数段，收尾规则在 CLOSE-RECORD / RULE-3。改技能文档前先分别核对这三处，再统一副本；卡面里的「实测结论」本身也要过一遍 help/源码，否则会把错误的修正命令化。
