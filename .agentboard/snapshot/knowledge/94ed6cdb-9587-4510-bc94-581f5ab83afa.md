# 凭据过期检测与刷新设计（ACC-TOKEN）

## 1. 需求

用户原话：「token 会过期，要检测 token 是否过期，过期后要在账号旁显示刷新按钮（你调研怎么刷新，实在无刷新方法重新登陆也行）」。

拆解：检测（不解密也要能知道快过期了）→ 展示（账号行旁的状态徽标与刷新按钮）→ 刷新（能自动续期就自动续期，不能就引导重新登录）。本页是下游两张实施卡（服务端 1ca9ac4d、Web 4d8c5172）的契约来源。

## 2. 逐平台策略矩阵

refresh_method 按可行性取优先级 refresh_token > recapture > relogin；每格出处编号见文末「来源与证据索引」。

| 平台 | token 形态 | 到期来源 | 检测方式 | refresh_method | 刷新实现要点 | 失败降级 | 证据出处 |
|---|---|---|---|---|---|---|---|
| workbuddy_desktop | 桌面线 accessToken/refreshToken 是 `$wbEncrypted` 信封（AES-256-GCM，密钥在客户端原生模块，离线不可解）；插件线 accessToken 是明文 Keycloak JWT（iss=`https://www.codebuddy.cn/auth/realms/copilot`） | 桌面线 info 文件 `auth.expiresAt` **明文毫秒**（本机实测：lastRefresh→expires 恰 30 天，refreshExpires 60 天）；插件线 JWT exp（本机实测 iat 2026-11-04 → exp 2026-12-04，30 天） | 主动：捕获/导入时读 expiresAt 明文字段或解 JWT exp（JWT 已有 jwtSubject 同款解析先例）；被动：签到 401 | `recapture`（客户端自续期，本机 lastRefreshTime=2026-11-07 当天；重读桌面线 info / 插件线 info / 进程内存导出） | refresh-credential 内部转发现有 `capture-current`（CLIENT_NOT_RUNNING 时先试 `backfillCheckinCredentialFromPlugin`，该分支已存在）；写行时同步 expiresAt；桌面线 token 本身解不开不影响——到期字段是明文 | recapture 拿不到有效凭据（文件缺失/refreshExpiresAt 也过期）→ `relogin`（workbuddy_oneid 协议加号） | G2 实测；G7 §3；F8 capture/backfill；F3 workbuddy poll |
| minimax | opaque：accessToken 60 字符 `mmoat_` 前缀、refreshToken 60 字符 `mmort_`（均非 JWT） | auth.json `expiresAtMs`（本机实测 2026-11-07 当天剩 ~4.8h）；device grant 响应 `expires_in`（秒） | 主动：expires_at 列；被动：签到 401（CHECKIN_CREDENTIAL_INVALID） | `refresh_token`（凭据载荷 JSON 含 refresh_token 时）；旧裸串载荷 → `recapture` | **已实现**：`refreshMinimaxCredential` — POST `{account.minimax.cn\|account.minimax.io}/oauth2/token`，form `grant_type=refresh_token&refresh_token=…&client_id=mcode-public`；响应 access_token 必须有，refresh_token 有则换新、无则保留旧的；`expires_in`→`expires_at` 落载荷 | HTTP 400 `invalid_grant`（refresh token 被官方客户端轮换作废）→ 置 invalid → `relogin`（minimax_device，RFC 8628+PKCE） | F1 实现；G3 实测；G11 契约；G13 卡面调研 |
| trae | RS256 JWT（`Cloud-IDE-JWT` 前缀，~1004 字符；claims 只有 data/exp/iat） | 信封 payload `expiredAt` == JWT exp（本机实测 iat 2026-11-04 → exp 2026-11-18，14 天）；payload 另有 `refreshToken`/`refreshExpiredAt`/`tokenReleaseAt` 字段 | 主动：capture 解信封读 expiredAt 或 JWT exp（解信封代码已存在，秒级）；被动：401 | `recapture`（客户端自续期后重读 storage.json 信封） | **现状缺口：captureCurrent 只把裸 token 落 vault，refreshToken/expiredAt 被丢弃**——须改为落 JSON `{token, refresh_token, expires_at}`；refresh-credential 转发 capture-current（只需读信封，不需要停机冷快照） | storage.json 不可读 → `relogin`（trae_oauth 本地回调 17388） | G1 实测；G7 §1；F7 capture；G6 §2 Trae |
| qoder_cn | 桌面 token `dt-` opaque（27 字符）+ refreshToken `drt-`（28）；PAT `pt-` 长期不刷新 | auth.v1.dat 明文键 `expiresAt`/`refreshTokenExpiresAt` **字段名已确认、数值未读**（safeStorage DPAPI，需客户端同链解密） | 主动：暂不可（无 capture provider，registry `PROVIDER_NOT_IMPLEMENTED`）；被动：未来额度 401 | `relogin`（qoder_device 设备流；PAT 直填属另一添加入口） | 无已实现捕获/刷新链路；凭据在客户端 DPAPI 内，服务端不自取；加号线 poll 只落 dt- token，无 refresh token | PAT（`POST /api/v1/jobToken/exchange`，长期兜底不刷新） | G7 §2；G6 §2 Qoder；F9 registry |
| zcode | `oauth:bigmodel:access_token` JWT HS512；`zcodejwttoken` JWT HS256 **无 exp** | bigmodel token 是否带 exp **未验证**（本机 credentials.json 信封解密失败，见 §6）；zcodejwttoken 无 exp，可能按 `token_version` 服务端失效 | 主动：不可（无已知 exp）；被动：额度接口 401（反证：zcodejwttoken 打 quota 端点已被实测拒绝，正确令牌是 bigmodel access_token） | `relogin`（zcode_cli 轮询流） | 本机 credentials.json **没有** `oauth:bigmodel:refresh_token` 键（实测键位只有 access_token/user_info/active_provider/zcodejwttoken/project-key-location）；CLI poll 是否下发 refresh_token 未验证；加号线只落 access_token | zcode_cli 重登；国际区走 zai 授权（双区互斥，登录即清对方） | G4 实测；G10 §2/§3；F3 zcode poll；G9 §2 |

CLI 四来源（一行口径，不进矩阵；`credential_status` 恒 `unknown`，不出刷新按钮）：

- deepseek：`sk-` API key，长期，无过期字段 → 不会过期。
- opencode_go：配置文件里的 key，长期 → 不会过期。
- codex：无登记凭据（额度取自 sessions），登录态在客户端 auth.json 由 CLI 自管 → 不归本设计管。
- commandcode：`~/.commandcode/auth.json` 的 API key，长期 → 不会过期。

## 3. 数据设计

硬约束：DPAPI 单次解密实测 5–9s（PowerShell 子进程 Protect/Unprotect，F16）→ **列表接口绝不逐账号解密** ⇒ 到期时间与失效标记必须在写入时落库，列表只读列。

新增列（`managed_account`，纯加法，幂等 `ALTER TABLE ADD COLUMN`）：

| 列名 | 类型 | 语义 |
|---|---|---|
| `credential_expires_at` | INTEGER（epoch ms，NULL=未知） | 写入点从载荷 JSON / JWT exp / 明文字段提取 |
| `credential_status` | TEXT NOT NULL DEFAULT 'unknown' CHECK(in 'valid','expiring','expired','invalid','unknown') | 落库基准值；读取时按 now 与 expires_at 即时修正 expired/expiring |
| `credential_refresh_method` | TEXT NULL CHECK(in 'refresh_token','recapture','relogin') | 平台静态表 ⊕ 载荷能力（minimax 载荷无 refresh_token 时降 recapture） |
| `credential_invalid_at` | INTEGER NULL | 最近一次凭据被服务端判失效（401 / invalid_grant）且未恢复的时间 |

迁移：新文件 `apps/server/src/db/migrations/credentialExpiry.ts`，`migrateCredentialExpiry(db)` 逐列 `PRAGMA table_info` 检查后 ADD COLUMN（照抄 `deviceIdentity.ts` 模式，F11）；在 `apps/server/src/db/schema.ts` 的 `initSchema` 里 **`migrateDeviceIdentity(db)` 之后注册**（F12）——同样必须排在 accountPlatforms / checkinPlatforms 这类 DROP+CREATE 重建 managed_account 的迁移之后，否则加列被重建带走。老数据不回填（不解密），保持 `unknown`，由下一次写入点自然补齐。

status 判定规则（GET 列表时逐行计算，不解密）：

1. `credential_invalid_at` 非空且晚于最近一次成功刷新 → `invalid`；
2. `credential_expires_at` 非空：`now >= expires_at` → `expired`；`expires_at - now <= 24h` → `expiring`；否则 `valid`；
3. 其余 → `unknown`。

expiring 阈值 24h 说明：minimax access token 生命周期约 5–7h，会常态 expiring——这是预期信号（该刷新了），徽标用中性色不算告警。

写入点（谁负责填列）：

1. `credentialImport.importCredentials`（导入线，F5）：`entry.expires_at` → credential_expires_at；minimax 带 refresh_token → refresh_method=`refresh_token`，workbuddy/trae → `recapture`；status 按到期推导。
2. `addAccountAuthorization.pollAddAccountAuthorization` authorized 分支（协议加号线，F4）：`AddAccountPoll` authorized 形态扩展可选 `expires_at?: number | null`（minimax 用 `expires_in*1000+now`；workbuddy/zcode/qoder 从 token 响应字段透传，取不到 null）；`upsertAccount` 同步写三列。**minimax 加号线须同步改为落 JSON 载荷 `{access_token, refresh_token, expires_at}`**——现状 pollAuthorization 校验完 refresh_token 后只把裸 access_token 装进 credential 丢弃（F3），与 ACC-FIX-5 捕获线口径不一致。
3. `captureCurrent`（桌面捕获，F6/F7/F8）：minimax 已落 JSON（ACC-FIX-5）；**trae 须补** payload.refreshToken/expiredAt 落 JSON（现状只 protect 裸 token，F7）；workbuddy 桌面线读 info 文件 `auth.expiresAt` 明文字段（无需解密，G2）。
4. `checkinRunner.withRefresh` 续期成功（F2）：写回 vault 后 UPDATE 行 `credential_expires_at=新值, credential_status='valid'`，清 invalid_at；续期失败/重试仍 401 收尾 `CHECKIN_CREDENTIAL_INVALID` 时：`credential_status='invalid'`, `credential_invalid_at=now`。
5. 未来额度查询 401：与 4 共用同一 helper（建议 `markCredentialInvalid(db, accountId, now)` / `markCredentialRefreshed(db, accountId, expiresAt)`，放 repos/managedAccount.ts）。
6. refresh-credential 端点（§4）：成功写 valid+expires_at；invalid_grant 写 invalid+invalid_at。

## 4. 接口设计

### GET /api/managed-accounts（扩展，向后兼容）

每行新增三字段（shared `PublicManagedAccount` 同步扩展，声明可选以兼容既有测试 fixture，F15）：

- `credential_status: 'valid'|'expiring'|'expired'|'invalid'|'unknown'`
- `credential_expires_at: number|null`
- `refresh_method: 'refresh_token'|'recapture'|'relogin'|null`

实现：列值直接 SELECT（零解密）；status 落库值做基准、服务端按 §3 规则用 now 即时修正（保证「落库 valid 但实际已过有效期」的行不会失真）。

### POST /api/managed-accounts/:id/refresh-credential

- **Idempotency-Key 必需**（UUID）：一次性 refresh token 不得重复发送，重放返回首次结果；复用 `idempotencyInput(req, true)` + idempotency 表（与 checkin-authorizations/start 同口径，F10）。
- 请求体：`{}` strict（空对象；actor 由 idempotencyInput 读取）。
- 执行：`runAccountOperation(db, {account_id, app_id, client_instance_id, operation:'capture'}, …, {tryLock: true})`（F13）。operation 枚举 CHECK 现有四值，不为其重建 account_operation 表——复用 `'capture'`（语义「凭据捕获/续期」），失败码用 `CREDENTIAL_*` 前缀并登记进 SAFE_ERROR_CODES。tryLock=true：同账号刷新串行，抢不到锁立即 409 ACCOUNT_BUSY。
- 按 refresh_method 分派：
  - `refresh_token`（minimax）：解密该账号凭据 → `parseMinimaxCredential` → 复用 `refreshMinimaxCredential` → 成功：新载荷 vault.protect → UPDATE 行（checkin_credential_ref、credential_expires_at、status=valid、清 invalid_at）→ 旧 ref vault.delete → 202。
  - `recapture`（workbuddy/trae）：转发 `requireProvider('capture')` 的现有 captureCurrent（workbuddy 客户端未跑先走 backfillCheckinCredentialFromPlugin，与 capture-current 端点现有分支一致）。
  - `relogin` 或 null：**不发任何平台请求**，直接 409 CREDENTIAL_RELOGIN_REQUIRED。
- 成功响应 202：

```json
{ "account": { "…PublicManagedAccount 字段…": "", "credential_status": "valid", "credential_expires_at": 1796357488000, "refresh_method": "refresh_token" }, "refreshed": true, "method": "refresh_token" }
```

- 错误码与中文文案：

| HTTP | code | 文案 | 说明 |
|---|---|---|---|
| 404 | ACCOUNT_NOT_FOUND | 账号不存在 | |
| 409 | ACCOUNT_BUSY | 该账号有进行中的账号操作 | tryLock 未抢到 |
| 409 | CREDENTIAL_RELOGIN_REQUIRED | 该账号的凭据无法自动刷新，请重新登录 | refresh_method=relogin/null，或 refresh grant 返回 invalid_grant（minimax HTTP 400）；body 附 `{reason_code, app_id}` 供前端开向导 |
| 409 | CREDENTIAL_REFRESH_FAILED | 刷新凭据失败，请稍后重试或重新登录 | refresh grant 网络/非 2xx/缺字段；recapture 平台的其它失败透传原码（如 TRAE_STORAGE_MISSING） |
| 409 | CLIENT_NOT_RUNNING | 客户端未运行，无法读取最新登录态 | recapture 且客户端离、backfill 也没有 |
| 503 | VAULT_UNAVAILABLE | 凭据保护不可用 | DPAPI 失败 |

- relogin 引导：错误响应 body 带 `app_id`（= 向导要预选的平台），不需要新端点。

### 并发与幂等

- 同账号串行：runAccountOperation 账号级锁（F13），刷新与签到/捕获/切换互斥。
- Idempotency-Key 重放：同一键返回首次结果（withIdempotencyResult），双击/网络重试不会二次消费 refresh token。
- minimax refresh token 一次性+轮换：刷新成功即写回 vault 并删旧 ref；失败（含 invalid_grant）只试一次，不循环（与 ACC-FIX-3 withRefresh 同口径，F2）。

## 5. UI 行为

- 账号行（AccountCard）徽标与按钮：
  - `invalid`：红色「凭据已失效」+ 主按钮「重新登录」；
  - `expired`：红色「凭据已过期」+ 主按钮「刷新凭据」；
  - `expiring`：中性黄「约 x 小时后过期」+ 次要按钮「刷新凭据」；
  - `unknown`：灰字「凭据状态未知（捕获或重新导入后可检测）」，无按钮；
  - `valid`：无额外元素。
- 点击「刷新凭据」→ POST refresh-credential（带 Idempotency-Key；请求期间按钮禁用防重复）：
  - 202：invalidate `managed-accounts` 查询，徽标按新 status 重渲染；
  - 409 CREDENTIAL_RELOGIN_REQUIRED，或点击「重新登录」：打开添加账号向导并预选平台。
- **向导预选实现**：`AddAccountEntry` 已按平台挂载（prop `app`，testid `accounts-add-<app>`，F14）。方案：把 open 状态提升/支持受控——AccountsPanel 增加状态 `reloginApp: ManagedAppId | null`；refresh 调用收到 CREDENTIAL_RELOGIN_REQUIRED 时写入该状态；`AddAccountEntry` 接受 `initialOpen?: boolean`（`app === reloginApp` 时为 true），对应平台向导自动展开并聚焦「开始授权」。向导轮询 authorized 后已有 invalidate managed-accounts 逻辑（F14），徽标自动恢复。
- relogin 未完成前账号行保持 invalid 徽标；向导取消/失败徽标不变。
- dist 未重建约定与本页无关；Web 卡实施时按 TEST-PAGE 在 5174 验证。

## 6. 关键流程与未验证项/风险

### 关键流程（时序）

1. **主动检测**：列表加载 → SELECT 三列（零解密）→ 服务端即时修正 status → 前端按徽标规则渲染。
2. **refresh_token 刷新**（minimax）：点击 → 幂等键 → tryLock → 解密单份凭据（5–9s，单账号可接受）→ POST oauth2/token → 200：写回 vault + 更新行 → 202 → 前端刷新列表。
3. **recapture**（workbuddy/trae）：点击 → tryLock → provider.captureCurrent（读本机文件/信封/插件线）→ 更新行（含 expires_at）→ 202。
4. **被动检测**：签到（未来含额度查询）401 → withRefresh 刷新一次 → 成功写回+valid；失败 → invalid + invalid_at → 账号行显示「凭据已失效」。
5. **relogin**：刷新端点/按钮 → 409 CREDENTIAL_RELOGIN_REQUIRED(body 带 app_id) → 前端开向导预选平台 → 授权成功（行更新）→ 徽标消失。

### 未验证项

1. WorkBuddy 插件线 Keycloak refresh_token grant 未实测（端点按 realm 惯例推断为 `/auth/realms/copilot/protocol/openid-connect/token`，本轮未发线上请求）；第一版走 recapture，无阻塞。
2. Trae refresh_token grant 端点与签名链路未验证（信封有 refreshToken/refreshExpiredAt 字段；icube-dc 键内含 EC P-256 私钥疑用于刷新签名，G7 §1）；第一版走 recapture。
3. Qoder auth.v1.dat 的 expiresAt 数值未读（需客户端同链 DPAPI 解密；capture provider 未实现）；其 refresh grant 端点未调研。
4. ZCode bigmodel access_token 是否含 exp 未验证：本机 credentials.json 信封解密失败（前一 worker 按 G10 推导密钥解密未成功，与该页「5/5 解密成功」冲突——可能客户端版本更换 fallback 密钥或键位；本轮按纪律未重试）；CLI poll 响应是否含 refresh_token 未验证。
5. MiniMax refresh grant 实机验证未跑：refresh token 一次性+每次轮换+同账号单会话互踢，无人值守不跑（G11/G13 同口径）；服务端续期成功后客户端侧 auth.json 旧 token 是否立即失效需真机确认。
6. expiring 阈值 24h 对 minimax（5–7h 生命周期）意味着常态 expiring——预期行为，待用户验收反馈再调。

### 风险

- **MiniMax 刷新与客户端互踢**：服务端续期成功后，官方客户端同账号会话可能被踢下线（G12 §切换 3 实证客户端会自轮换并使捕获凭据失效）；刷新成功提示文案应建议「如客户端被登出，请重新捕获本机凭据」。
- **WorkBuddy recapture 依赖客户端自续期**：客户端长期不跑时插件线 JWT 到期，refreshExpiresAt（60 天）也过期后只能 relogin。
- **DPAPI 成本**：refresh-credential 单账号单次解密可接受；列表/批量路径绝不解密（§3 硬约束）。
- **存量账号首次显示 unknown**：现库 4 行（G5）都无 expires 列值，需用户点一次「捕获当前账号」或重新导入才落 expires_at；unknown 文案已写明出路。
