# 外键索引缺口扫描与 comment_count 全表扫描定位（PERF-5）

## 结论

`issue_comment` 原先只有 `id` 主键；`GET /api/issues` 的 `comment_count` 是逐行相关子查询
`(SELECT COUNT(*) FROM issue_comment c WHERE c.issue_id = i.id)`，无 `issue_id` 索引时每张卡一次全表扫描。
生产库副本 665 行实测：加索引前 p50 706ms / p90 1227ms，加索引后 p50 54ms / p90 88ms，comment_count 全对。

## 扫描方法（可复跑）

打开库（只读副本即可），对每张用户表跑 `PRAGMA table_info` 拿列、`PRAGMA index_list` + `PRAGMA index_info` 拿已索引列，
筛出「列名以 `_id` 结尾但不在任何索引首列/成员里」的项，再人工排除非外键语义（`workspace.last_migration_id`）与 FTS 内部表（`knowledge_fts.page_id`）。
命中候选用 `EXPLAIN QUERY PLAN` 逐条核实是否真为 `SCAN <表>`，避免把已有复合索引覆盖的列误判为缺口。

## 本次扫描结论（2026-11-07，生产库）

高价值缺口：`issue_comment(issue_id)`（本卡已修）、`message(session_id)`（会话消息列表，建议下一张卡）。
中低价值：`session(workspace_id/issue_id/...)`、`approval_rule(issue_id/session_id/turn_id)`、`session_step_ledger(session_id)`、
`account_operation(account_id)`、`issue(session_id/last_seen_comment_id)`、`issue_decision*`、`checkin_*` 等，原理相同但表小或主路径已有可用索引。

## 迁移写法与位置

- 独立 `migrations/<name>.ts`，单条 `CREATE INDEX IF NOT EXISTS`，幂等、不重建表、不改列。
- 必须在 `initSchema` 的**最末**调用：此前任何 issue 表重建（STATUS-1 等）都会带走表上索引，放最末可幂等补回。
- 索引名带表名前缀（`idx_issue_comment_issue`），与 `idx_issue_parent` / `idx_issue_dep_blocker` 风格一致。

## 验证套路

1. `PRAGMA index_list(issue_comment)` 含新索引；连续跑两次 `initSchema`，`sqlite_master` 中该表索引结构不变。
2. `EXPLAIN QUERY PLAN SELECT COUNT(*) FROM issue_comment c WHERE c.issue_id=?`：`SCAN c` → `SEARCH c USING COVERING INDEX ...`。
3. 真实 `createApp` 打 `GET /api/issues?workspace_id=<id>`，逐行比对 `comment_count` 与 `SELECT COUNT(*) ... WHERE issue_id=?`。
4. 计时用生产库**副本**（`.db` + `-wal` + `-shm` 一起复制），各 20 次取 p50/p90，不碰线上库。

## 坑

- 只给 `issue_comment` 加索引不等于 `/api/issues` 整体最优：其余聚合列（dependency/decision/child）各自也有子查询，后续仍应看完整计划。
- 计时前不要跑 `ANALYZE`：它会改变外层查询计划（`SEARCH i USING INDEX` 变 `SCAN i`），前后对比口径就不一致了。
- 生产实例不重启时索引不生效：迁移在 `initSchema` 里，随下次启动幂等落地。
