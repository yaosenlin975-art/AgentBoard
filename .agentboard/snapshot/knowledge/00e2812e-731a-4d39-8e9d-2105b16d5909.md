# 全仓代码审查（2026-11-07）沉淀的可复用事实

配合 Docs/audit-2026-11-07-code-review.md（15 条结论、13 张卡）使用。本页只留可复用的事实与判断口径，不复述逐条清单。

## 1. issue 列表不缺 workspace_id 索引（推翻常见假设）

只读打开中心库（40MB）执行 EXPLAIN QUERY PLAN：`SELECT * FROM issue WHERE workspace_id = ? ORDER BY sort_order, created_at, id` 命中 `issue_parent_order`（(workspace_id, parent_id, sort_order)）。因此「列表全表扫」不成立，不要再为此立项。
真实成本在附加列：comment_count（PERF-5 已修索引）、4 个决策投影子查询、dependency_violation 的 recursive CTE（每行一次，成本随阻塞子树大小增长）。

## 2. 启动期单例锁的正确顺序（CR-1 / 3eb48104 已落地）

不变量：acquireServerLock 必须先于 openDb / initSchema（全部迁移）/ sweepExpiredLeases / recoverOnBoot。
修正前的形态：四件事都在加锁之前执行，与同文件「必须先于 openDb」的注释相反；并发启动时两个进程同时走「PRAGMA table_info 判断列是否存在 → ALTER TABLE」，后到者抛 duplicate column name 且在加锁前就崩掉。
现在的顺序（apps/server/src/index.ts `main()`）：loadConfig → 生成 instanceId/startedAt → 注册 wireWorkspaceDbCloseOnExit → acquireServerLock（拒绝则 exit 4）→ 注册 releaseServerLock 退出钩子与 SIGINT/SIGTERM → mkdir → openDb → initSchema → sweepExpiredLeases → createWorkspaceDbRouting → recoverOnBoot → createApp → listen。
即锁现在覆盖的启动步骤：openDb、全部 schema 迁移、租约清扫、启动恢复（打开工作区库）、createApp 装配与 listen。被拒绝的后到进程不碰库、不清租约、不建 attachments 目录。
退出钩子注册顺序有意保持「先关工作区库、后放单例锁」（exit 钩子按注册顺序执行），否则新实例可能在旧实例还在 checkpoint 工作区库时接手。
推论：任何新增的启动期迁移/清扫都必须放在加锁之后；单例锁只能依赖 configDir / dbPath / port，不能依赖 DB 句柄，否则又会被迫把加锁点后移。

## 3. 三端 HTTP 超时口径（CLI 侧已由 CR-3 / b759a183 落地）

- MCP（apps/mcp/src/apiClient.ts）：10s 超时（AbortController + setTimeout）。
- CLI（packages/cli/src/api.ts）：统一 15s（REQUEST_TIMEOUT_MS）；每次 fetch 尝试独立 AbortSignal.timeout，超时不参与 GET 重试（避免总耗时翻倍）；fetch 阶段与响应体读取阶段（decodeWithTimeout）映射为同一可读文案「服务无响应：<METHOD> <path> 超过 15s 未完成（<base>）…」，写请求追加幂等重试指引；退出码沿用请求失败=1。超时识别按 cause 链查 error.name：Node undici 对 AbortSignal.timeout 的原生拒绝形态是 TimeoutError（DOMException，code=23），旧版可能包装为 AbortError，两种都接。
- Web（apps/web/src/api/client.ts）：15s / 上传 60s（竞速实现，见 a99b3eb7）。
- 判断口径：服务进程存活但不回包时三端都应在自身档位内非零退出/终态报错；三端任一新增请求入口，都应先对齐超时语义再谈其它。

## 4. 错误码映射边界（CR-7 / 3cc1c822 已落地）

apps/server/src/api/routes.ts 的 errorHandler 顺序固定为：ApiError → INVALID_JSON → entity.too.large → SQLITE_BUSY(409 DB_BUSY) → SQLITE_CONSTRAINT*(400 CONSTRAINT_VIOLATION) → SQLITE_READONLY*(503 DB_READONLY) → 500 INTERNAL。
- 约束错误按扩展码前缀归并（SQLITE_CONSTRAINT_CHECK / _UNIQUE / _FOREIGNKEY / _PRIMARYKEY / _NOTNULL…），message 只带约束类别，不回 better-sqlite3 原始文案与 SQL；
- **例外 SQLITE_CONSTRAINT_TRIGGER 仍走 500 INTERNAL**：它是 schema 里 RAISE(ABORT) 主动拒绝（如 attachments 的评论事务回滚保护），语义是服务端内部拒绝而不是调用方参数错误；把前缀一刀切映射成 400 会打挂 test/attachments.test.ts 的既有 500 断言；
- 只读库（快照归档、权限受限、磁盘降级）写失败是服务可用性问题，给 503 而不是 400/500；
- 回归保护：apps/server/test/errorMapping.test.ts 用真实 better-sqlite3 错误对象（同库临时表造 CHECK/UNIQUE/TRIGGER 违例、只读连接写）经真实 createApp 全链路断言状态码与 error.code。
推论：新增约束仍要在路由层确认映射；测试不要手写伪造 code——用真实 SQL 造错才覆盖得到扩展码形态（手写 'SQLITE_CONSTRAINT' 测不出 _CHECK / _TRIGGER 这类后缀）。

## 5. labels 是 TEXT 无 JSON 约束（CR-5 / 2547aeca 已落地）

`issue.labels` 存 JSON 字符串但没有 CHECK 约束：一行脏值（手工改库、旧版本写入、外部工具）会让读取路径 JSON.parse 抛错，整个看板列表 500。
- 读取侧：db/repos/issue.ts 的 tryParseLabels 只接受「JSON 字符串数组」，坏 JSON / 对象 / 数字数组 / null 一律返回 null；parseLabelsOrEmpty 按 [] 渲染，不改写库；
- 启动侧：services/labelIntegrity.inspectIssueLabels 只读全表体检，index.ts 在加锁后的启动流程里落日志（脏行数/总行数 + 最多 10 个 issue id），不改数据；
- 验收口径：test/labelIntegrity.test.ts 用真实 createApp 断言列表/详情 200 且脏卡 labels=[]；启动日志行用**一次性探针**取证——隔离 APPDATA/AGENTBOARD_DB/AGENTBOARD_PORT/AGENTBOARD_LOG 起真实 `dist/index.js`，预置一行脏 labels 后断言日志出现 `启动体检：1/2 …：<issue id>`。该探针不进测试套件：在进程内跑 main() 会留下全局副作用，牵连 idempotency / knowledgeNudge 等用例。
推论：新增任何「TEXT 存 JSON」的列都照此办理（读取兜底 + 启动体检只读报数），不要指望 DB 约束。

## 6. 已核查、判定「非缺陷」的怀疑点（避免重复排查）

- SQL 全参数化，无模板串拼值；
- attachments 以 UUID 作存储键，无用户可控路径拼接；
- pick-folder / credentialImport 用 spawn + 数组参数，无 shell；
- 两处 dangerouslySetInnerHTML 均为模块常量样式，非用户内容；
- voiceRoutes 的 250ms ticker 在 close/finish 双路径清理；
- decodeTreeCursor 对非法游标抛 ValidationError（400），不是 500；
- 账号凭据不进日志与界面。

## 7. 服务端全量测试的三个实测坑

- 单例锁集成测试必须跑构建产物（`dist/index.js`）：测试先断言 dist 不旧于 src，否则测的是旧行为；改了 `src/index.ts` 却没 build 时应当直接失败而不是假绿。
- 用 spawn 起真实服务的测试必须持续排空 stdout/stderr 管道。全量并行测试时日志量变大，管道缓冲写满会把子进程卡死，表象是后续 `fetch` 报 `failed`（会被误判成服务挂了）。
- 这台 16 逻辑核机器上全量并行跑（vitest 默认 15 worker）会有 5–10 个时序敏感用例（桌面壳模拟、WS 推送顺序、git on done）超时抖动；把 `--testTimeout` 抬到 30s 或减少 worker 后它们全部通过，逐文件隔离跑也是全绿。判定「是不是自己改坏了」时先单跑可疑文件，不要直接归因。
- 多会话并行时工作区里常混着别人未提交的半成品（如 `gitBaseline.ts` 报 `changed is not defined`，或 `platformQuotaParsers.ts` 删掉测试仍在 import 的常量），全量结果会被污染。要证明「我的改动不破坏现有测试」，用 `git worktree add --detach <dir> HEAD` 建 HEAD 干净树、只叠加本卡文件，再把 `node_modules`、`packages/shared/dist`、`packages/adapters/dist`、`packages/adapters/node_modules`、`packages/shared/node_modules` 用 junction 链回主树后跑全量，比 stash 别人的改动安全；先在 worktree 里 `tsc -p tsconfig.build.json` 生成 dist，单例锁用例才不会因缺产物失败。
- 补充（CR-9 实测）：当本卡改动不含别人的脏文件时，`git stash push -- <仅本卡文件清单>` 收起自己的改动、在「改前」状态逐文件复跑可疑用例做 A/B，比 worktree+junction 轻得多；前提是本卡文件集与他人脏文件不相交（收工后 `git stash pop` 恢复）。

## 8. Web issues 域路径注册表（CR-9 / 1e8b0085 已落地）

`apps/web/src/api/endpoints.ts` 是 issues 域唯一拼路径的地方（listIssues / getIssue / createIssue / patchIssue / deleteIssue / releaseIssue / markIssueDone / listIssueTree / listIssueCounts / getIssueDependencies / addIssueDependencies / removeIssueDependency / listIssueComments / addIssueComment / listIssueAttachments / listIssuePendingAttachments + 常量 ISSUE_DRAFT_PATH）。其余域（sessions / workspaces / chat / knowledge / accounts）仍散落，按「其余域渐进」处理：哪张卡动到哪个域，就把该域字面量迁进 endpoints.ts 或同层新域文件。
约定：组件与 lib 一律调函数或常量，不再自拼 `/api/issues*`；URL 与参数逐字保持迁移前形态（id 为服务端 UUID，encodeURIComponent 前后恒等）；组件私有响应类型用函数泛型透传（listIssueCounts<T> / listIssuePendingAttachments<T>），不让 api 层反向 import 组件。
复算（endpoints.ts 之外代码字面量应为 0）：`cd apps/web && grep -rEn "[`'/\"]/api/issues" src/components src/lib src/state src/api --include="*.ts" --include="*.tsx" | grep -v "src.api.endpoints" | grep -vE ":[0-9]+: *(//|/\*|\*)" | wc -l`
