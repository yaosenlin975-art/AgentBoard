# 待验收积压分档与复核口径

2026-11-09 对 134 张「待验收」卡做首轮分档（采集方式：kb list-tasks --status 待验收 + 逐张 kb show --json，取 description 与全部评论正文）。

## 分档口径

- **A · 本机可复跑（126 张）**：卡面或评论中能匹配到本仓真实提交（7–40 位 hash 在 `git log --all` 中有前缀命中），且至少有一条可执行复算命令或明确的测试结果。
- **B · 只有自述/截图，缺复算命令（8 张）**：有提交或结论，但卡面与评论中没有可直接执行的命令，或只给了截图/自述。
- **C · 需真机目视或依赖外部环境（0 张严格口径）**：本机完全无法复跑。实际分档中为 0；「剩余缺口需要真机目视 / 第三方界面」的卡随 A 档复核时单独标注并现场起真实实例，不预先一刀切。

## 复核规则（不放水）

1. **提交校验**：短 hash 不能与全长 hash 直接相等比较，必须做前缀匹配；再 `git show --stat <sha>` 核对改动文件与卡面声明一致。
2. **点名复跑**：只复跑卡面/评论点名的测试文件或 CLI 命令，不用全量回归代跑；复跑命令与输出写进卡评论。
3. **放行条件**：提交存在 + 改动面与卡面一致 + 点名测试通过或 CLI 行为可复现，三条齐才 `kb accept --verdict pass` + `kb close`。
4. **退回条件**：缺上述任一，`kb reopen --to 进行中` 并在评论写清缺什么、补什么命令能过。
5. **不放行依据**：仅凭「看起来没问题」「截图」「他人转述」一律不算。
6. **回避规则**：他人正在处理或刚新建的卡（例如 2026-11-09 21:12–21:16 另一会话新建的 4 张待规划卡）不入本批次，不抢、不改。

## 批次

每 10–20 张一批，批次结论写在当批卡评论与回报里；本页只维护口径与张数，不写完成流水。
