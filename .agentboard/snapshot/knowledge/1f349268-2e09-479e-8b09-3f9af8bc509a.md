# kb decisions --issue 的服务端过滤（OPT-12 核验）

## 结论

`kb decisions --issue` **已经**走服务端过滤，不存在「拉 200 条前缀再前端筛」的问题。开工核验后确认实现由 DEC-4 引入：

- CLI：`decision.ts` 先 `resolveIssueByRef` 拿到完整 issue，再用 `workspace_id` + `issue_id` 组 query；不带 `--issue` 时 query 里没有 `issue_id`，旧输出逐字不变。
- 路由：`GET /api/decisions` 把 `issue_id` 原样交给仓储。
- 仓储：`listDecisions` 在 `WHERE d.issue_id=?` **之后**才 `LIMIT 200`，因此目标卡的决策即使排在全区分页窗口之外也能命中。

本卡（OPT-12）因此没有改生产代码，只补齐了回归测试与真机核验，防止后续有人把 `issue_id` 过滤挪回客户端。

## 回归测试

1. `apps/server/test/decisionIssueFilter.test.ts`（新增 3 例）：
   - 构造 205 条他卡决策（created_at 均晚于目标卡）+ 1 条目标卡决策（最旧）；
   - 断言不带 `issue_id` 时默认 200 条窗口**装不下**目标卡决策（证明场景真实存在）；
   - 断言带 `issue_id` 时能查到该条（过滤在 LIMIT 之前），且不混入他卡。
   - 注：决策用 `state='answered'` 构造，避开「同一 issue 最多一条 open/grace」的唯一索引，与窗口逻辑无关。
2. `packages/cli/test/decision.test.ts` 增强 2 例：
   - `--issue` 的列表请求 URL 必须含 `issue_id=<uuid>` 且不带 `limit=`；
   - 不带 `--issue` 时 URL 不含 `issue_id=`（旧口径不变）；
   - 另加空结果用例：输出 `（无决策）`、退出码 0。
