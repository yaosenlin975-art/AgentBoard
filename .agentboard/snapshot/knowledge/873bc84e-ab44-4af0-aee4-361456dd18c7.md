# 列表查询成本归因与「--all <300ms」不可达的实测边界

结论：`kb list-tasks --all` 的端到端 300ms 目标在「每条命令一个 node 进程 + HTTP 拉整区」的架构下不可达，且**瓶颈不在 CLI 侧**，而在服务端 `comment_count` 相关子查询（`issue_comment` 缺 `issue_id` 索引）。本页固化测量方法与成本拆分，复测时不必重做对照实验。

## 一、可复用的测量方法

1. **端到端计时**：`[Diagnostics.Stopwatch]` 包住 `kb …` 命令，stdout 重定向丢弃（不含终端渲染），含 node 进程启动与模块加载；每组 12 次，多配置交替跑以抵消时段漂移，每轮先探活服务端（本次 `failed_rounds=0`）；统计 p50 / p90 / min / max / mean 并保留原始序列。
2. **请求数计数 + 回退模拟**：起一个计数反代（`127.0.0.1:18787 → 8787`），按路径累计请求；`/__mode?block=1` 把 `/api/statuses` 直接打成 404，等价于旧服务端（回退分支），其余请求原样转发。这样「带聚合端点 vs 回退逐区」可在同一进程上往返切换，不需要重启服务或改代码。
3. **固定开销地板**：`node -e ""`（纯进程启动）、`kb --version`（CLI 模块图加载）、以及「最小工作区 + 2 次请求」的真实命令，三者给出任何优化都绕不开的下限。
4. **字段成本拆分**：对同一端点用 `fields=` 逐个加列做 curl 计时，把总耗时归因到具体投影列；不要只测「有 fields / 无 fields」两档。

## 二、基线数字（663 卡 / 7 工作区 / 本机）

- `kb --version` p50 169ms（min 139，偶发 618~633 双峰，杀软冷扫描）；`node -e ""` p50 29ms。
- 最小工作区真实命令（16KB 负载、2 次请求）p50 243ms、min 231ms —— 已吃掉 300ms 预算的 8 成。
- `kb list-tasks --all`：9 次请求（1 workspaces + 1 statuses + 7 issues），p50 1792ms，p90 3092，min 1284，max 4520（12 次）。
- `--tree`：2 次请求，p50 807ms（阈值 800ms 已贴边）。
- 服务端 `/api/issues?workspace=e41eb0fb…&fields=…`（663 行、465KB）单次 0.61~1.79s；7 次在 better-sqlite3 同步执行下串行，累计 ≈1.3s。

## 三、字段成本（e41eb0fb，663 行，每组 3 次）

| 投影 | 耗时 |
| --- | --- |
| 极简 6 字段（id/title/status/priority/parent_issue_id/labels） | 10~25ms |
| 仅加 `comment_count` | **1139~1278ms** |
| 仅加 decision 四列 | 11~12ms |
| 仅加 children 两列 | 7~28ms |
| 仅加 dependency_violation | 8~27ms |
| 当前 `LIST_TASK_FIELDS` | 465KB / 0.61~1.79s |

## 四、根因

`apps/server/src/db/schema.ts` 的 `issue_comment` 只有 `id` 主键，没有 `issue_id` 索引；`apps/server/src/db/repos/issue.ts:54-55` 的 `COMMENT_COUNT_COLUMN` 是逐行相关子查询 `(SELECT COUNT(*) FROM issue_comment c WHERE c.issue_id = i.id)`，663 行即 663 次全表扫描。加索引（`CREATE INDEX IF NOT EXISTS idx_issue_comment_issue ON issue_comment(issue_id)`，沿用 `migrations/claimLease.ts` 的幂等写法）即可把这一项降到毫秒级。

## 五、为什么即使修了索引也达不到 300ms

- 固定开销 169ms（CLI 模块加载）+ 7 次往返 + ~940KB JSON 解析 + 663 行表格渲染；当前最小工作区真实命令已 231ms。
- 服务端归零后预估端到端 400~500ms。要真正压到 300ms，只能改变测量口径（不计进程启动）或引入常驻进程/本地缓存，属架构级取舍，不是 CLI 参数优化能解决。

## 六、聚合端点（`GET /api/statuses`）的真实价值

- 普通 `--all`：带聚合 9 请求 vs 回退 9 请求，耗时不可区分（不过滤自定义状态时字典用不上，聚合只是把「本来不会发生的逐区字典请求」提前成 1 次）。
- `--all --status <自定义>`：聚合 9 请求 vs 回退 16 请求，但省下的是 2ms 级小请求，p50 差异仍在噪声内。
- 结论：它的收益是**请求数卫生**，不是 wall time；评估这类端点时不要把请求数下降直接等同于耗时下降。

## 七、复算命令

- 卡数：`curl -s "http://127.0.0.1:8787/api/issues/counts?workspace_ids=e41eb0fb-c367-43cf-a99d-6dc5239a5694"`
- 字段成本：`curl -s -o NUL -w "%{time_total} %{size_download}" "http://127.0.0.1:8787/api/issues?workspace=e41eb0fb-c367-43cf-a99d-6dc5239a5694&fields=id,title,status,priority,parent_issue_id,labels,comment_count"`
- 进程地板：`kb --version`（10 次取 p50）；请求数：反代 `/__stats`
- 索引现状：`PRAGMA index_list('issue_comment')`；计划：`EXPLAIN QUERY PLAN SELECT COUNT(*) FROM issue_comment WHERE issue_id=?`
