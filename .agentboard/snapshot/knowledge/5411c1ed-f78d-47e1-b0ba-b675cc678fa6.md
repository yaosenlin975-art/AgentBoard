# 账号授权地址用无痕窗口打开（ACC-INCOGNITO）

## 为什么放在服务端

- 账号授权抽屉要求「开始授权」与手点「授权地址」都直接弹**无痕**窗口，与账号平台无关（minimax / zcode / qoder_cn / workbuddy_desktop / trae 共用一条链路）。
- 前端无法指定普通窗口：`window.open` / `<a target="_blank">` 只能走用户默认浏览器的普通窗口；桌面壳 `desktop/src-tauri` 没有 opener 插件（壳只做窗口/托盘/服务生命周期）。
- 因此由本机服务 `POST /api/browser/open-incognito` 拉起系统浏览器。与既有 `/api` 一致无鉴权，安全前提是服务只监听回环（单机工具）。

## 选择顺序与参数

| 平台 | 候选（按顺序） | 参数 |
| --- | --- | --- |
| Windows | Chrome → Edge → Brave，各探测 LOCALAPPDATA / ProgramFiles / ProgramFiles(x86) 三处常见路径 | Chrome/Brave `--incognito --new-window`；Edge `--inprivate --new-window` |
| macOS | `open -na "Google Chrome"` → `open -na "Microsoft Edge"` → Brave | `--args --incognito` / `--args --inprivate` |
| Linux | google-chrome → chromium → microsoft-edge → brave-browser | `--incognito --new-window` |

Chrome/Edge 已在运行时，带 `--incognito`/`--inprivate` 仍会在既有进程里开一个新无痕窗口，不需要额外 `--user-data-dir`（加了反而会起一套干净 profile，用户会丢登录态）。

## 降级口径（用户必须能感知）

- 找不到任何 Chromium 系浏览器 → 用系统默认浏览器打开普通窗口，返回 `mode='normal'` + 中文 `degraded_reason`。
- 前端必须把 `degraded_reason` 展示在向导内，否则用户会误以为这次也是无痕窗口——降级本身不算失败，静默降级才算。
- 连默认浏览器都起不来 → 502 `BROWSER_OPEN_FAILED`，`details.attempts` 带每个候选的失败原因，便于排障。

## 前端接线（ACC-INCOGNITO-W，2026-11-08 落地）

- REST 调用统一走 `apps/web/src/api/browserOpen.ts` 的 `browserOpenApi.openIncognito(url)`（ACC-INCOGNITO-CLIENT），组件层不再在 `addAccountApi.ts` 重复封一份。
- `AddAccountWizard`：`start()` 拿到 `authorization_url` 后 fire-and-forget 调无痕打开（不 await，打开慢不阻塞「取消 / 检查授权结果」按钮）；「授权地址」`<a>` 改点击拦截（`preventDefault` 后调同一函数），**href 保留**供右键复制/查看，`target="_blank"` 已删。
- 降级提示 testid `accounts-add-degraded-<app>`（role=status，amber 色）：只在 `mode==='normal'` 出现，文案原样用服务端 `degraded_reason`（本地兜底「已用系统默认浏览器普通窗口打开（非无痕）」）；`mode==='incognito'` 恒无提示且清掉旧提示。打开失败只进既有失败 notice（中文主文案 + 可展开技术码），不影响会话继续。

## 测试坑（web 侧）

- `src/test/setup.ts` 的 msw 是 `onUnhandledRequest: 'error'`：向导测试里任何触发新网络请求的交互都必须配 handler，否则整文件红。点「开始授权」的用例现在都要补 `POST /api/browser/open-incognito` handler。
- 会话 pending 时组件每 3 秒自动轮询：用例耗时可能超 3 秒，没断言轮询的用例也要给 `POST /api/add-account-sessions/:id/poll` 一个 pending 兜底 handler，避免慢机器上偶发未处理请求报错。
- 断言「默认导航被阻止」：document 冒泡阶段挂 click 监听读 `event.defaultPrevented`（React 18 委托在根容器，document 监听后触发）；「未调用 window.open」用 `vi.spyOn(window, 'open')`。

## 约束与坑（服务端）

- 只接受 http/https、长度 ≤2048；其它协议一律 400 `BROWSER_URL_INVALID`（避免被当成打开本地文件的通道）。
- `spawn` 一律用参数数组、不经 shell 拼串；Windows 降级用 `cmd.exe /d /c start "" <url>`，空标题参数不可省（否则 cmd 会把 URL 当窗口标题）。
- 只等子进程 `'spawn'` 事件并 `unref()`，不等退出——浏览器是长期进程。
- 单测必须注入 fake `spawn`/`existsSync`，否则会真的弹窗；服务端用 `BrowserOpenerDeps` 注入位（`RouterDeps.browserOpener` / `CreateAppOptions.browserOpener`）承载。
- 接线探针：用真实 `createApp` + supertest 打端点断言 200（RULE-3），只挂单测 router 不算外部可触达。
