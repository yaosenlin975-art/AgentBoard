# 适配器层 ask 事件与回答回填（CHAT-ASK-1A）

## 协议契约

- `UnifiedEvent` 新增 `ask`：`{ type:'ask', request_id, question, options: [{ label, description? }], step_id: string | null }`；既有成员（text/thinking/tool/error/end）不变。
- `TurnHandle` 新增**可选** `answer?(requestId, answer): Promise<void>`：只有声明提问能力的适配器实现（当前仅 codebuddy），消费方必须判空；不实现不影响 codex/opencode/dsh。
- 提问工具名走**精确白名单** `ASK_TOOL_NAMES = new Set(['AskUserQuestion'])`；不在白名单的 `tool_use` 仍发 `tool` 事件（原降级行为保留，不得回归；大小写变体不算提问）。
- `request_id` 取 `tool_use` 块的 `id`；缺失时用本轮序号 `ask-<n>`（解析状态新增 `askSeq`）。`step_id` 取 assistant `message.id`，缺失为 `null`。
- 入参兼容 `{questions:[{question,options}]}`（取第一问）与扁平 `{question,options}`；options 支持字符串数组或 `{label,description}` 对象数组。残缺入参不抛错，缺字段落空串/空数组。

## 回填通道（spawn 层）

- `SpawnLineOptions.keepStdinOpen`：写入 `stdinText` 后不 `end()`，stdin 常驻可写；未设置时保持原行为（写完立即 end）。
- `LineChild.writeStdin(chunk)`：失败以 `StdinWriteError` reject（code = `STDIN_UNAVAILABLE` / `STDIN_CLOSED` / `STDIN_WRITE_FAILED`），不抛同步异常。
- stdin 常驻时必须挂 `'error'` 监听（EPIPE 等），否则会成为未处理的 stream error 直接崩进程；写失败仅 reject 当前 promise。
- 回填报文：一行 JSON `{"type":"user","message":{"role":"user","content":[{"type":"tool_result","tool_use_id":<request_id>,content:<回答>}]}}` + `\n`（与提问 tool_use id 对应）。

## codebuddy 落点与限制

- 仅 `--input-format stream-json` 的轮次（当前实现中即带图片轮次）保持 stdin 可写并支持回填；`-p <prompt>` 参数模式的 stdin 为 ignore，ask 事件照常发出，但 `answer` 以 `STDIN_UNAVAILABLE` 拒绝（不会静默丢弃）。
- 回填幂等与拒绝口径：同一 request_id 只允许一次（重复 → `ALREADY_ANSWERED`）；未知/过期 → `UNKNOWN_ASK`；轮次结束后 → `TURN_ENDED`；写 stdin 失败 → `STDIN_WRITE_FAILED` 且**不**标记已答（允许重试）。
- stream-json 轮次由「写完初稿即 end」改为 keep-open，真实 CLI 是否必须 EOF 才开始处理未联调验证（单测覆盖的是假进程）。

## 集成注意（CHAT-ASK-1B 必做）

- 新增 union 成员后，`apps/server/src/services/sessionManager.ts` 的 broadcast 事件类型（只列 text/thinking/tool/error/end）会编译失败；1B 需同步扩展 WS 事件类型并把 ask 接到 `markTurnAwaiting`。本卡按边界未改 server 任何文件。

## CHAT-ASK-DEFER：真实 CLI 的 deferred 形态（2026-11-10 实测，codebuddy 2.179.2）

- 模型不会直接产出 `tool_use: AskUserQuestion`；它先 ToolSearch，再发 `tool_use` 名为 `DeferExecuteTool`，入参 `{ toolName:'AskUserQuestion', params:{ question, options } }`。只认精确白名单会永远等不到 ask。
- 归一规则：`DeferExecuteTool` 且 toolName 命中白名单（兼容 `mcp__server__AskUserQuestion` 前缀）→ 复用 parseAskEvent（request_id 用外层 tool_use id，input 换成 params）；其他 toolName 或缺少 params 仍走普通 tool 事件。
- 端到端实测（隔离实例 8799 + 线上库热备副本 + 独立 APPDATA，WS 真连，非 fixture）：ask 事件 → `session.turn awaiting_input`（reason=ask_user，message 为提问原文）→ `POST .../answer` 200 → 同一 turn 立刻回 `running`、awaiting_json 清空；`session_turn` 行数不变（1），步骤账本继续新增（s8–s11），子进程 PID 不变并继续输出工具事件。
- 落差：以 `tool_result(tool_use_id=外层 call id)` 写 stdin 能解除阻塞并让同一轮继续；但本机 CLI 在该轮随后调用 Bash 时会停住（Bash/Read 的审批/执行通道属 CHAT-APP 链），因此本轮未自然走到 done。ask 链路「收到 → 回答 → 同轮继续」已验证，轮次收尾依赖审批通道就绪。
- 前置条件：只有 `--input-format stream-json`（当前 = 带图片轮次）的 stdin 可写；纯 `-p <prompt>` 轮次 ask 照常发出但无法回填（`STDIN_UNAVAILABLE`）。
