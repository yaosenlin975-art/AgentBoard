## 是什么

知识页正文平时只在库里（`knowledge_page.body_md`），git 里看不到。BORROW-5.1 在每次 **create / revise / archive（含 restore）** 之后，额外把该页写一份可读快照到：

```
<工作区>/.agentboard/snapshot/knowledge/<page_id>.md
```

并**只提交这一个路径**。库仍是唯一事实源，快照是派生物：删掉文件不影响数据，提交失败也不影响知识页写入——但**提交失败必须可观测**（见「客户端可观测」）。

## 文件格式

front matter 字段顺序固定（同一 revision 重复渲染逐字节一致，避免无意义 diff）：

```
---
id: <page id>
slug: <slug>
title: <title>
scope: workspace
revision: <n>
status: active|archived
updated_at: <ISO8601>
---

<正文>
```

`status` 必须写：归档页的快照若仍标 active，会被误读成活跃内容。

## 提交口径

- `git add -A -- <path>` + `git commit -m "knowledge(<slug>): r<n> <title>" -- <path>`：路径限定，绝不整索引提交，避免把并行卡已暂存的改动卷进来。
- 内容未变化（例如只改了不进快照的字段）时不造空提交：返回 `committed=true`，`commit` 指向已有 HEAD。
- 仓库没配 `user.name`/`user.email` 时补 `-c user.name=AgentBoard -c user.email=agentboard@local`（与 GIT-ON-DONE 同口径，不覆盖已有署名）。

## 状态规则

| 动作 | 文件处理 |
| --- | --- |
| create / revise / restore | 重写同一路径，front matter 的 `status` 跟随库 |
| archive | 重写同一路径，`status: archived`，文件保留（可 restore） |
| delete（软删） | 删除文件并提交删除；库已视该页不存在，留可读正文等于泄漏已删内容 |
| 快照不存在时 delete | 不造空提交，`committed=false` + `skipped=true`，`reason` 说明「快照文件不存在，无需提交删除」 |
| 快照从未入库、只删掉本地文件 | 同上，`skipped=true`（没有可提交的变更 ≠ 提交失败） |
| `/pages/import` 批量导入 | **不接线**（KB-SNAP-IMPORT 方案 3 定案，2026-11-08）：一次请求写多页，与「只含该页路径」冲突；响应 `page_commit` 恒为 `{ committed: false, skipped: true, reason, … }` 显式跳过信号，不是失败 |

## 失败语义（验收 3「失败回滚不留半提交」）

- 写文件或 git 失败：新建的文件删掉、已有的还原到改动前内容，并尽力 `git reset -q HEAD -- <path>` 清掉暂存，返回 `committed=false` + `reason`。
- 回滚自身失败（KB-SNAP-ROLLBACK，2026-11-08）：`rollback_failed=true`，原因以 `；回滚失败（<还原快照文件|清暂存>）：<git stderr>` 拼进同一 `reason`，服务端 `console.error` 留痕（含 relative_path）；工作树/索引可能残留该页路径，需人工 `git status` 检查，不重试。`git add` 未成功时不调 reset、不算回滚失败（索引里没有本次内容，锁未释放导致的 reset 失败是噪音，保证单失败时 reason 只报原始失败）。
- **不回滚知识页**：库是事实源，提交失败只在响应 `page_commit.reason` 里告知，不让派生物失败变成数据写失败。
- `reason` 格式：`<失败阶段> 失败：<git stderr 首行>`（阶段 = `写入快照文件` / `git add` / `git status` / `git commit`）。**不能只取 `Error.message`**：`execFileSync` 的 message 首行是 `Command failed: git add ...`，真正原因（如 `fatal: Unable to create '...index.lock': File exists`）只在 `stderr` 里。
- 软删是例外：文件先删、再提交删除；git 失败也不还原文件（删除态优先），`reason` 说明原因。

## 客户端可观测（KB-SNAP-SILENT，2026-11-07）

`page_commit = { path, relative_path, committed, commit, reason, skipped? } | null`（`null` = `scope=common` 或没有对应工作区）。

- **`skipped=true`**：`committed=false` 但**不是失败**（无快照可提交 / 无变更），客户端不报警、不判失败。
- **`skipped` 缺失或 false 且 `committed=false`**：真实失败，视为「正文已保存、审计链已断」。
- CLI（`kb knowledge create/revise/action`）：文本模式**与 `--json` 模式一致**——`stderr` 打印快照路径 + `原因：<reason>`，**exit 1**。`--json` 的 stdout 仍是单个页面 JSON（失败信号看退出码与 `page_commit`，不插入错误 JSON）。
- 为什么选「stderr + exit 1」而不是只打印原因：正文写入成功但 git 审计链缺失属于**部分失败**，exit 0 会让调用方与脚本把它当完全成功；`--json` 保持单个 JSON 文档，机器读取不受污染。
- 不要原样重跑：revision 已前进，同一 `--expected-revision` 会撞 CAS（exit 2）。先修 git（常见残留 `.git/index.lock`），再按新 revision 重跑。

## 接线与验证

- 三个写端点（`POST /pages`、`PUT /pages/:id`、`POST /pages/:id/actions`）响应新增 `page_commit`；`scope=common` 或无对应工作区时为 `null`（只做工作区页）。
- 单测 + 真实 app（`createApp` + supertest）覆盖 create → revise → archive → restore → delete 五步：每步 `git show --name-only --format=HEAD` 都只含该页路径，删除后工作树 `git status --porcelain` 为空。
- 失败分支用**真实 `.git/index.lock` 注入**验证（不是 mock）：`apps/server/test/knowledgePageCommit.test.ts` 断言 `committed=false`、`reason` 含 `git add 失败` 与 `index.lock`、文件仍是旧 revision、HEAD 未变；同一文件里另有 app 级用例断言 `PUT /api/knowledge/pages/:id` 仍返回 200 但 `page_commit.committed=false`。`packages/cli/test/knowledge.test.ts` 覆盖文本 / `--json` / `skipped=true` / `committed=true` 四种 CLI 行为。

## 坑

- **只认绝对路径的工作区**：相对路径（如单测里的占位 `'A'`）会以服务进程 cwd 为基准，把快照写进 `apps/server/A/...` 并提交到真实仓库。已在路由侧接线处拦截：非绝对路径直接返回 `committed=false` + 原因，不落盘。曾因此让知识相关单测把 11 个快照文件提交进真实仓库，需清理。
- `PUT /pages/:id` 的 zod schema 是 strict，**不收 `slug`**：复用创建 payload 做修订会 400，需先摘掉 `slug`。
- 创建端点自 KB-CR-1 起 `domain` 必填，测试 payload 漏掉会 400。
- 该文件曾被他人在飞改动写入 UTF-8 BOM，导致全局 `check-bom` 红；写仓库文件一律走无 BOM 路径（编辑器 / `fs.writeFileSync` / `UTF8Encoding($false)`）。
- 工作区不是 git 仓库或仓库不健康时，功能降级为「只写文件不提交」，原因在 `page_commit.reason`，不阻断知识页写入。
- 单测验证仓库干净时，跑完要比对 `git rev-parse HEAD` 前后一致，不能只看断言通过。
