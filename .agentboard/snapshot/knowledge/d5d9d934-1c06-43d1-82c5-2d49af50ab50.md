# 首屏四段耗时分解与切工作区卡顿归因（PERF-3 审查结论）

> 本页是审查结论与测量口径，不含实施进度。完整量化表、逐项证据与复算命令见仓库 `Docs/audit-2026-11-07-perf3-first-screen.md`。

## 1. 四段定义（可复用的口径）

首屏必须拆成四段，否则「慢」无法归因：

1. **挂载**：HTML 解析到 React 首次渲染（FCP 之前）。
2. **首个数据请求发出**：挂载 → `Network.requestWillBeSent` 命中首个 `/api/*`。
3. **首屏可用**：首个数据请求发出 → 第一张任务卡出现在 DOM。
4. **稳定**：首屏可用 → 网络静默（无在飞请求、无 longtask）。

**必须把进程/冷启动地板单独列出**，不能算进「数据慢」：实测 `node -e ""` 约 59ms、`kb --version` 约 209ms 是模块加载与进程起步成本，与 SQL/渲染无关。若把地板混进「首屏 2.2s」，会把排查方向错引到数据库。

产物页（`apps/web/dist`）实测中位：FCP 261ms / 骨架 240ms / 首个 issues 请求 227ms / 响应落地 829ms / 首卡 2172ms / 稳定 2215ms。该 2.2s 全部发生在「请求发出 → 首卡」，与地板（~0.2s 级）不同量级。

## 2. 根因清单（均带实测）

- **R1 列表 SQL 被缺失索引拖垮**：`issue_comment` 只有 `id` 主键、无 `issue_id` 索引 → `comment_count` 相关子查询 `SCAN c` 逐行全表扫描。663 行时：`i.*` 8.71ms，加上 `comment_count` 立刻 795.14ms；完整列表 SQL 622.83ms，去掉 comment_count 的 19 列查询 5.21ms。修复已另有【PERF-5】`c98392ac-22f8-4e08-b638-f2bec6f532f6` 负责，本页只作归因引用。
- **R2 同一 URL 全量取两次**：看板主查询 `['issues', ws]`（Board.tsx）与标签筛选 `['issues', ws, 'labels']`（workspaceLabels.ts）各拉一次 `GET /api/issues?workspace=`，互不复用。单条 1,555,766 B；首屏 API 合计约 3.2MB，其中 1.56MB 纯重复。
- **R3 WS 失效风暴**：服务端写评论后连发 `comment.added` + `issue.changed` 两帧；`ws.ts` 把 `comment.added` 映射为 `['issues']` 全域前缀失效，`issue.changed` 映射为 `['issues', ws]` → 一次评论 = 4 条全量 + 1 条 counts = 6,223,064 B；仅改状态 = 2 条全量 = 3,111,532 B。
- **R4 加载态与真空态不可区分（A 类）**：Board 用 `issues ?? []`，Column 对空数组渲染「暂无任务」；切工作区时列表先清空（采样 57ms:0 … 290ms:0，blank=true），空列持续 230–700ms。
- **R5 计数用 0 冒充加载态（A 类）**：WorkspaceCard 在 `statusCounts === undefined` 时把统计格渲染成 0（源码注释「先按 0 渲染」），闪 0 窗口实测 164/180/221ms。
- **B 类已不成立**：counts 端点实测 1 请求 / 956B / 4.4ms / 27 行；「计数永远为 0」的截图对应 07:51 的旧 dist 产物，不是当前源码缺陷。

## 3. 数据慢 vs 渲染慢的判定

- 缓存命中切换：281/364ms、0 请求，属于纯渲染成本。
- 663 卡 → 8310 DOM 节点，纯渲染 281–364ms；longtask 合计 161–316ms，最长 133–160ms。
- **窗口化阈值定在 1500 卡**：当前 663 卡未到，先不做窗口化（做了只会增加复杂度与滚动同步成本）；到 1500 卡再评估。

## 4. 踩过的坑（后续复用）

- **`dist` 落后源码会让产物页结论失效**：本次 dist 构建于 07:51，而 `WorkspaceCard.tsx`/`WorkspaceList.tsx` 改于 08:44，抽屉相关数字只能取源码页（vite dev 5199）。测量前先比对 `dist` 时间戳与源文件 mtime。
- **不要直接连线上库做基准**：同库单例锁会干扰，且写操作污染真实数据。用 `VACUUM INTO` 生成快照 + 独立 `APPDATA` + `AGENTBOARD_DB` + 独立端口起隔离实例。
- **请求重复的归因要看 initiator 栈**：仅看 URL 会误判为 StrictMode 双发；`Network.requestWillBeSent.initiator` 能直接指到 `WorkspaceCard.tsx` 与 `workspaceLabels.ts` 两个 queryFn。
- **不要用 setTimeout/假骨架/删功能换体感**：骨架必须挂在 `isPending` / `statusCounts === undefined` 这类真实状态上，否则只是把问题藏起来。
- **禁用「0 当默认值」**：加载中渲染 0 与真实 0 在视觉上无法区分，是 A 类缺陷而非优化空间。
