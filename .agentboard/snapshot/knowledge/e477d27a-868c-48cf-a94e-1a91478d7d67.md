# 看板渲染 memo 化与详情防抖卸载 flush

## 结论（可复用做法）

### 1. 让 memo 真正生效：先保证 props 引用稳定

`Column` / `IssueCard` 套 `React.memo` 本身不省一次渲染，前提是上游 props 引用稳定。看板里必须一起处理的引用源：

- `useWorkspaceStatuses` 里 `names` / `byName` / `statuses` 每次渲染都新建数组或 Map → 下游 `useMemo([columns])` 永远失效。修法：在 hook 内用 `useMemo` 按 `query.data` 引用缓存这三项（`statuses` 依赖 `fromServer/query.data/workspaceId`，`names`/`byName` 依赖 `statuses`）。
- `columns` 稳定后，`grouped = useMemo(() => groupByColumn(visibleIssues, columns), [visibleIssues, columns])` 才有意义；否则每次渲染都重建各列数组，所有列 props 全变。
- `runningSessionIds`（Set）、`onToggleSelect`、`onCreateIssue`、`onReleaseRunning`、`sortControl`（JSX 元素）都是每次渲染新建的引用，会把 `Column` memo 打穿。分别用 `useMemo`（Set、元素）与 `useCallback`（回调）。注意这些 hook 必须写在「未选工作空间提前 return」之前，否则 hook 数量随分支变化。
- 搜索框每次 keystroke 必然改变 `visibleIssues`，各列内容确实要变；memo 的收益是「仍然命中筛选的卡片，其 `issue` 对象引用未变 → `IssueCard` 直接跳过重渲」。所以 `IssueCard` 的 memo 才是逐键重渲的主收益点，`Column` 的 memo 主要挡住弹窗、选择态等无关状态变化。

### 2. 防抖保存必须在卸载/切卡时 flush

详情面板的字段保存是 500ms 防抖 PATCH（`description` / `priority` / `labels` / `due_*`）。只在卸载时 `clearTimeout` 会把窗口内的改动整批丢掉（静默数据丢失）。

- 抽出 `sendPatch(body)` 作为唯一保存路径；定时器到期与卸载 cleanup 都走它。
- 抽出 `takePending()`：先取走再清空 `pendingRef`，保证定时器与 cleanup 不会重复发送同一批字段。
- cleanup 的依赖写成 `[sendPatch, takePending]`（`sendPatch` 依赖 `issueId`）：这样不只是组件卸载，**切换卡片（issueId 变化）也会 flush 旧卡**，且用的是旧 `issueId` 闭包，不会写到新卡上。
- 标题不走这条防抖路径（`TitleInlineEditor` 提交即 PATCH），所以「防抖丢失」的回归用例要用描述/优先级/标签等字段写。

## 验证口径

- 回归用例：改描述后在 500ms 窗口内 `unmount()` → 断言只发 1 次 PATCH 且 body 为新描述 → 用全新 QueryClient 重新挂载（强制走 GET）→ 断言预览读到新值。
- 看板侧跑 `board.test.tsx` / `boardColumns.test.tsx` / `boardColumnsFive.test.tsx` / `boardDisplaySelection.test.tsx`，交互语义不变（拖拽、选择、分组、空列新建）。

## 坑

- `apps/web/src/test/detail.test.tsx` 里 `DispatchDialog > 派发响应返回剩余数后保留弹窗并允许显式续用会话发送下一批` 在 HEAD 上同样失败（body 为空、找不到 `attachment-batch-notice`），属存量红灯，与渲染/防抖改动无关；判断「是不是自己弄红的」要用 HEAD 单文件对照。
- 做基线对照**不要用 `git stash`**：工作区可能有别人留下的 stash 条目，`git stash pop` 会误取别人的改动并制造冲突。改用「复制到临时目录 → `git checkout HEAD -- <单文件>` → 跑测试 → 复制回来」。
