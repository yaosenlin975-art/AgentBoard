### 1.3 根因

1. **CLI 会拆、API 不会拆**：`kb create-issue -l "a b"` 走 `parseLabels`（`packages/cli/src/commands/createIssue.ts:12-19`，`split(/[,，\s]+/u)` + `trim` + 去空 + `Set` 去重），而直接调 `POST /api/issues` 传 `labels: ["a b"]` 会原样入库——上表「未拆分整串」全部来自这条路径。
2. **技能条款只在 using-agentboard 一处**，建卡时不一定被读到；且条款是「建议性」的（≤4 个、领域词），没有可机械检查的判定。
3. **没有「先用现成词」的默认动作**：智能体建卡时倾向用当前任务名当标签（`CHAT-*`、`BOARD-*`），而不是查现有高频词。

## 2. 规则

### 2.1 何时打

- **打**：新卡属于可被检索的领域工作（功能/缺陷/调研/文档/规则/测试/工具链/依赖/清理/验收）。
- **不打**：纯协调卡（父卡、汇总卡、追踪卡）——层级用 `--parent`，不占标签位。
- **不重复打**：已有卡不再追加同义标签（`UI` 与 `web` 不并存，见 2.3）。

### 2.2 打几个

- **1–3 个**为主，硬上限 4 个（沿用现有条款）。
- 一个标签必须能单独回答「按这个标签筛，我会想看到这张卡吗」；答否即删。

### 2.3 从哪取词（优先级）

1. **先查现有词表**：`kb list-tasks --workspace <当前> --json` 统计标签频次，优先复用 ≥5 次的高频词（当前 Top 12 见 1.1）。
2. **再查是否已有同义**：同义词对只保留一个——`UI` → `web`；`mcp` / `adapters` / `docker` / `git` → `工具链`；`语音` / `unslop` 这类项目名，若已 ≥6 次可保留为领域词，否则并入 `功能`。
3. **最后才造新词**：新词必须同时满足 ① 是稳定领域名词（不是卡号、不是任务代号）；② 预计后续 ≥3 张卡会用到；③ 单词、无空格、无日期。造新词时在卡评论写明理由。

### 2.4 词表基线（当前生效）

领域词（可自由使用）：`web`、`server`、`cli`、`工具链`、`知识库`、`账号管理`、`依赖`、`技能`、`测试`、`文档`、`调研`、`跨平台`、`功能`、`缺陷`、`规则`、`清理`、`验收`、`计划`。

## 3. 强制点（落地位置）

### 3.1 技能条款（using-agentboard「标签口径」节，已有，需补 3 条）

- 补「先查频次再取词」：建卡前跑一次 `kb list-tasks --json` 统计，优先复用 ≥5 次的高频词。
- 补「API 不拆分」警示：不经 CLI 直接调 `POST /api/issues` 时必须自己按 `[,，\s]+` 拆分并去重，否则整串入库。
- 补「同义词只留一个」映射表（见 2.3）。

### 3.2 建卡命令层（`kb create-issue`）

- 现状：`-l` 已按 `[,，\s]+` 拆分 + 去重（`parseLabels`）。
- 建议（需实现，属代码改动，本方案不执行）：`parseLabels` 后加**软告警**——命中禁用词表（见 4）时向 stderr 打一行提示但不阻断；标签数 >4 时同样告警。

### 3.3 服务端（`POST /api/issues`）

- 建议（需实现）：`labels` 数组中任一项含空格或逗号时，按同一规则拆分后再入库；或直接 400 拒绝并提示「标签请用 CLI 或先自行拆分」。
- 二选一属**待裁决**（见 6.1）。

## 4. 反例清单（禁止作为标签）

| 禁止类型 | 反例 | 正确做法 |
| --- | --- | --- |
| 日期 / 版本 | `用户需求2026-11-02`、`2026-11-03` | 时间用 `due_date` / `created_at` |
| 层级 | `父卡`、`子卡` | 层级用 `--parent` |
| 用户需求 + 日期 | `用户需求2026-11-03` | 用 `功能` / `缺陷` + 来源写进描述 |
| 含空格多词 | `规则 技能 文档 工作区边界` | 拆成 `规则`、`技能`、`文档`（≤4 个） |
| 卡号 / 任务代号 | `CHAT-DELETE01`、`BOARD-SEARCH`、`PANEL-MOTION01` | 卡号本身就是 id，不需要标签 |
| 过长短语 | 任意 >8 字的中文短语 | 拆成领域词 |
| 同义并存 | `UI` + `web`、`mcp` + `工具链` | 只留一个（见 2.3） |

## 5. 与标签过滤 UI 的对应关系

- 看板筛选条的数据源是「当前工作区所有卡的标签并集」，因此**每造一个新词都会直接出现在筛选条里**——这是「不造新词」的最强动机。
- 现状影响：95 个标签里 21 个是脏标签，占筛选条约 22%，用户每次筛选都要扫过它们。
- 建议（需裁决，见 6.2）：筛选条只展示「出现 ≥2 次」的标签，其余收进「更多」折叠区；或按 2.4 词表高亮，非词表词灰显。

## 6. 待裁决（需用户决定，本方案不替用户拍板）

1. **服务端遇未拆分标签时**：自动拆分后入库，还是 400 拒绝？（影响：旧客户端行为兼容 vs 数据洁净度）
2. **筛选条是否隐藏低频标签**（<2 次收进「更多」）？还是保持全量展示？
3. **是否允许智能体自由新增标签**：
   - 方案 A（严格）：只能从 2.4 词表选，新词需用户批准；
   - 方案 B（半开放）：可造新词，但需满足 2.3 三条并在卡评论说明理由；
   - 方案 C（开放）：不限制，仅靠清理卡定期收口。
4. **`语音` / `unslop` / `docker` / `git` / `mcp` / `adapters` 这类已有 ≥6 次的项目词**：升格为正式领域词，还是并入 `工具链` / `功能`？
5. **是否要对现存 21 个脏标签再跑一次清理**（可复用 `[TAG-CLEANUP-EXEC]` 的脚本/流程）？
