## 0. 现状盘点：为什么「很臃肿」

现详情由 `RightPanel` 壳 + `DetailPanel` 内容组成，所有块**同时铺开、无层级**：

| 现块 | 位置 | 占比问题 |
|---|---|---|
| 「任务详情」标题行 | `apps/web/src/components/right/RightPanel.tsx:264-278` | 与内容标题重复，白占一行 |
| 标题输入框 | `apps/web/src/components/detail/DetailPanel.tsx:256-268` | 标题永远是输入框，没有「阅读态」 |
| 描述（预览/编辑切换） | `DetailPanel.tsx:270-299` | 长描述常驻，且外面再套一层边框容器 |
| 优先级（独立整行 select） | `DetailPanel.tsx:301-318` | 一个字段占一整行 |
| 状态（独立整行 select） | `DetailPanel.tsx:320-346` | 与优先级同级的整行 |
| 截止日期（整行 + 长提示 + 日期/时间/清除） | `DetailPanel.tsx:348-404` | 最占地方的一块，提示文案「可选；不填 = 不设截止」常驻 |
| 标签 chips | `DetailPanel.tsx:406-410` | 可保留，形态已压缩 |
| 操作区（「操作」小标题 + 最多 6 个按钮） | `DetailPanel.tsx:413-570` | 状态不同按钮不同，全部平铺在正文中间 |
| 依赖（4 个永久展开分组 + 常驻搜索框） | `DetailPanel.tsx:572-573` + `DependencySection.tsx` | 前置/被阻塞/关联/重复四组 + 空状态提示，首屏吃掉最多空间 |

## 1. 设计结论（逐条回答脑暴问题）

### 1.1 哪些信息必须常驻首屏

| 常驻项 | 形态 | 理由 |
|---|---|---|
| 标题 | 阅读态 2 行（窄屏 3 行），右侧一个修改按钮 | 标题本身替代「任务详情」；标题是最高频的识别信息 |
| 状态 | chip（点击可改）⚠ S1 | 决定「这张卡现在该做什么」，必须一眼可见 |
| 优先级 | chip（与截止同一横行） | 用户已拍板 |
| 截止 | chip（与优先级同一横行） | 用户已拍板；日期时间进 popover，不占行 |
| 负责人 / 占用 | chip（头像 + 名称 + 静默时长） | 「谁在干活」决定要不要留言 / 释放 |
| 依赖摘要 | 一行折叠头：`前置 2 · 1 未解除 · 阻塞 3` + 「暂不可领取」徽标 | 领取决策所需，但明细不必展开 |
| 描述 | 前 3 行 + 展开 | 快速判断任务是什么 |
| 最新 2 条评论 | 时间正序，底部输入框 | 协作主通道，不能藏 |
| 主操作 | 底部吸底工具条 | 任何滚动位置都能「下一步」 |

标题 + meta 行位于**固定 header**（不随内容滚动消失），这是「常驻」的实现方式。

> ⚠ 已废弃：上表「状态 chip（点击可改）」与「描述 前 3 行 + 展开」两项，分别见文末「已废弃 / Superseded」S1、S2。

### 1.2 哪些收进折叠区、默认展开还是折叠

| 折叠区 | 默认 | 说明 |
|---|---|---|
| 依赖明细 | 折叠 | 摘要常驻；未解除前置用琥珀色摘要 + 「暂不可领取」徽标透出，不展开也能做决策 |
| 关联会话 | 折叠 | 只有切聊天时才需要 |
| 活动记录 | 折叠 | 追溯用；**当前服务端没有 issue 级历史接口，需新接口（见未决 7）** |
| 附件 | 折叠 | 当前附件挂在评论里，独立折叠属「汇总视图」 |
| 原始 JSON | 折叠 | 开发排查用，普通用户不需要 |
| 审计证据 | 折叠 | 收尾证据，验收时才看 |
| 评论区「全部 N 条」 | 折叠（默认只显示 2 条） | 保留评论，但不让历史淹没当前对话 |

判断口径：**影响「现在做什么」的常驻；只在特定时刻查证的折叠。**

### 1.3 操作区放哪：底部吸底工具条（推荐）

**推荐底部吸底工具条 + 右侧 ⋯ 溢出菜单**，而不是右上角溢出菜单。

| 方案 | 优点 | 问题 |
|---|---|---|
| A 底部吸底（推荐） | 主操作始终可见；不随滚动消失；主/次层级天然分离；评论输入后不用回滚顶部 | 占约 44px 高度 |
| B 右上角溢出菜单 | 省高度 | 把高频主操作藏起来，「下一步做什么」不可见；右上角已被「编辑 / 关闭」占用，两个层级混在一起 |

规则：

- 主按钮随状态变化 ⚠ S1（已被推翻）：待规划→`派发任务`；进行中→`标记待验收`；待验收→`通过验收并关闭`（次要 `退回进行中`）；已关闭→`重新打开`。
- 危险 / 低频操作（强制释放、复制 ID、删除）进 `⋯`。删除仍需行内二次确认，确认区就在菜单内。
- 「会话进行中」不再作为禁用按钮占位，改为负责人 chip 表达占用状态，少一个死按钮。

### 1.4 依赖关系怎么显示才不占地方又不丢信息

- **首屏只留一行摘要**：`前置 2 · 1 项未解除 · 阻塞 3`；有未解除前置时整体转琥珀色，并挂「暂不可领取」徽标。
- 展开后按三组呈现，而不是现在的四组：`前置任务` / `被本卡阻塞` / `关联·重复（不阻塞领取）`。
- 每行：状态圆点 + 标题单行省略 + 状态文字；hover 看全名（真实实现用 `title` 或 tooltip）。
- 添加前置的搜索框只在展开区出现，不再常驻首屏。
- 信息不丢：未解除数量（决策）、标题与状态（展开后）、`related/duplicate` 关系（合组展示）、添加/移除入口（展开后）。

### 1.5 宽屏与窄屏（<920px 回落抽屉）差异

| 维度 | 宽屏（贴列 / 右侧抽屉 320–720px） | 窄屏（<920px 全宽抽屉，原型 390px） |
|---|---|---|
| 标题 | 2 行截断 | 3 行截断，顶部留出安全区 |
| meta 行 | 单行优先，放不下允许换行 | 明确允许两行：状态+优先级 / 截止+负责人 |
| 描述 | 3 行 clamp ⚠ S2 | 同样 3 行，但整宽 ⚠ S2 |
| 折叠区 | 同宽屏 | 同宽屏，行内标题省略更激进 |
| 操作条 | 主按钮 + ⋯ | 主按钮 flex 1，占满，⋯ 保留；底部加 `env(safe-area-inset-bottom)` |
| 关闭方式 | 外部点击 / Esc / 头部关闭 | 保留同样三种；不新增底部手势 |

关键取舍：**窄屏不再强求「优先级 + 截止」绝对同一行**——390px 下四个 chip 必然换行，强行同一行会挤压到不可读。宽屏满足用户基线，窄屏退化为两行（见未决 2）。

### 1.6 就地编辑的边界

| 场景 | 行为 |
|---|---|
| 进入编辑 | 点 ✎；显示单行 input（视觉上仍是标题位置，不新开一行）；焦点进入并置于末尾；显示计数与保存/取消 |
| Enter 提交 | trim 后校验；成功则更新标题、退出编辑、toast「标题已保存」 |
| Esc 取消 | 退出编辑，恢复原标题；若有改动则保留为草稿（下次进入编辑恢复并提示一次） |
| 空值 | 不提交，行内红字「标题不能为空，请填写后再保存。」+ 保留输入 |
| 超长 | 上限 200 字（待拍板）；>160 显示计数；超限红字「标题最多 200 字，当前 N 字（已保留你的输入）」并阻止提交 |
| 非法字符 | 单行 input 天然不接受换行；提交前 trim 首尾空白，剔除控制字符（`\u0000-\u001F`）；不折叠中间空格 |
| 编辑中来了新版本 | **不覆盖输入**；顶部横幅「此任务在你编辑期间被更新（12:04 · 其他人）」+ `载入最新版本` / `保留我的输入`；提交携带 `expected_updated_at`，409 时红字「保存冲突…」并保留输入，提供「仍然保存」 |
| 点击编辑区外部 | **不自动提交、也不自动取消**（保持编辑态）。自动提交会误保存，自动取消会丢输入；只有 Enter / Esc / 保存 / 取消能结束编辑 |
| 中文输入法 | 真实实现必须判断 `isComposing`，组词中的 Enter 不提交（原型未模拟） |
| 连点保存 | 保存中禁用按钮，禁止双 PATCH |

原型里用「模拟保存失败」复选框演示失败态：Enter 后出现可读错误且输入不丢。

## 2. 改哪些块、砍掉了什么

### 2.1 改（保留能力、换形态）

| 原块 | 新形态 | 原因 |
|---|---|---|
| 标题（输入框） | 阅读态标题 + ✎ + 就地编辑 | 阅读与编辑分离，减少常驻输入框的视觉噪声 |
| 优先级 select | meta chip + popover | 一行容纳四个决策项 |
| 状态 select | meta chip + popover（仍走 CAS） | 状态是最高频操作，chip 比下拉更轻 |
| 截止日期整行 | meta chip + popover（日期/时间/清除） | 去掉常驻提示文案与三个控件 |
| 标签 chips | 行内 chips（沿用 `LabelChipsEditor` 能力） | 形态已够紧凑 |
| 操作区 | 底部吸底：1 主 + ⋯ 溢出 | 主操作常驻，危险操作收口 |
| 依赖四组 | 一行摘要 + 三组折叠 | 首屏只留决策信息 |
| 关联会话 | 折叠行 | 非首屏必需 |
| 评论 | 首屏 2 条 + 「查看全部」+ 输入框常驻 | 评论是协作主通道 |
| 描述 | 3 行 clamp + 展开 ⚠ S2 | 长描述不霸屏 |

> ⚠ 已废弃：上表「状态 select → meta chip + popover」中的「点击可改」与「描述 3 行 clamp + 展开」分别见文末「已废弃 / Superseded」S1、S2。

### 2.2 砍掉（逐条）

1. **「任务详情」标题行** —— 用户已拍板，标题直接替代；无障碍用 `aria-label="任务详情"` 保留语义。
2. **「优先级」标签 + 整行 select** —— 被 meta chip 取代。
3. **「状态」标签 + 整行 select** —— 被 meta chip 取代。
4. **「截止日期（可选；不填 = 不设截止）」长提示 + 日期/时间/清除三控件常驻** —— 收进 popover，chip 只显示结果。
5. **操作区「操作」小标题和一排按钮** —— 收进吸底条与 ⋯。
6. **「会话进行中」禁用按钮** —— 改为负责人 chip 表达占用状态，去掉一个永远不可点的按钮。
7. **依赖区 4 个永久展开分组和常驻搜索框** —— 改为摘要 + 折叠 + 展开后添加入口。
8. **依赖空状态的三块提示**（无前置 / 没有阻塞 / 无关联 / 无重复） —— 摘要里显示 `0`，不再给每个空组各占一块。
9. **描述预览外加的一层边框容器** —— 正文直接铺在纸面上，少一层「盒子里套盒子」。

### 2.3 明确保留（不能因为「瘦身」丢能力）

- 派发前的 blocker 拦截清单；
- 强制释放 / 删除的行内二次确认；
- 标签联想与去重；
- 验收评论草稿（`AUDIT-DETAIL` 37ab55b2 已实现的能力）；
- 评论附件上传、图片投递状态、草稿 localStorage；

## 3. 视觉与交互契约

- 字号：标题 15px / 内容 12px / 元信息 10.5px；不做仪表盘式大字号。
- 圆角 6–11px；1px hairline 分隔；状态/优先级用极浅底色，不用大面积色块。
- 语义色只用 `--ab-accent`（进行中/警示）、`--ab-add`（已解除/通过）、`--ab-del`（高优先级/危险）。
- 动效：折叠用 `grid-template-rows: 0fr → 1fr`（160ms），chevron 旋转 90°；popover 3px 位移淡入；`prefers-reduced-motion` 全部压到 1ms。
- 焦点：标题编辑结束后焦点回到 ✎；关闭面板焦点回触发卡片（沿用现有 `RightPanel` 的 `returnFocusRef`）。
- 可访问性：折叠头是 `button[aria-expanded]`；toast `role=status`；错误区 `role=alert`。

## 8. 第二轮修订（2026-11-05 · DETAIL-REDESIGN-2）

### 8.1 修改一：编辑态只显示输入框，原文本整体让位

**根因**：`.title-display` 与 `.edit-bar` 都是 `display:flex`，类选择器优先级高于浏览器 UA 的 `[hidden]{display:none}`，所以进入编辑态后原文本并没有真正隐藏，出现「文字 + 输入框」并列。

**修复**（[index.html](index.html)）：

1. 全局兜底 `[hidden] { display: none !important; }`，任何带 `display:flex` 的块都不会再压过 `hidden`。
2. `#titleDisplay` 与 `#titleEditWrap` **互斥显示**：进入编辑只留输入框，退出恢复标题文本。
3. **无跳变高度锁定**：进入编辑前量出 `#titleDisplay` 的实际高度，赋给 `#titleEditWrap`（`.title-input` 是 `height:100%`）；退出时清空锁定，回到文本态自然高度。
4. 输入框**预填原文本**，光标放在**末尾**（不是全选）——继续补充标题的自然动作，也避免一进来就误键入覆盖原标题。
5. 提交成功 / Esc 取消 / 取消按钮都走同一个 `setEditing(false)`，清空高度锁，避免残留固定高度。

**实测高度**（真实浏览器，460px 面板）：

| 元素 | 文本态 | 编辑态 | 差值 |
|---|---|---|---|
| `#titleDisplay`（原文本） | 42.59px | 0（`display:none`） | 42.59px→0（语义正确） |
| `#titleEditWrap`（输入框容器） | 0 | 42.59px | 0→42.59px（语义正确） |
| `.title-row`（标题行整体） | 42.59px | 42.59px | **0px（≤2px，PASS）** |

**必须说明的一处差异**：整个 `.panel-header` 在编辑态会比文本态高约 **41px**，来源是第一轮既定的编辑工具条（计数 + 取消/保存，见 §1.6），不是标题文本/输入框互换造成的跳动。若用户要求「整个 header 也绝对零变化」，需要把工具条并入标题行（会压缩输入宽度）或改成浮层（会遮住首行内容）——列为新增未决 11，本轮不改，因为这两种做法都牺牲现有可用性。

### 8.2 修改二：图片内联 + 附件只做路径引导（两条独立语义）

原型里已拆成两条互不混用的语义：

| **图片内联** | 描述区与评论里直接渲染成图（`data-testid="desc-image"` / `comment-image`），点击开全屏灯箱，Esc / 遮罩 / 关闭按钮退出 | 图片是**内容**，参与 markdown 阅读流 |

### 8.3 四个可行性问题（逐条回答）

#### ① 图片来源：从哪进？

| 入口 | 代价 | 结论 |
|---|---|---|
| **粘贴截图（推荐主入口）** | 需要 composer / 描述编辑器的 paste 监听 + 剪贴板上传；`imageDraft.ts:27-33` 与 `NewIssueDialog.tsx` 已有可复用规则（PNG/JPEG/WebP、≤10MiB、每条最多 5 张） | **推荐**。最贴近用户「图片显示在评论和描述之中」的原话，截图是最常见来源 |
| **拖拽文件（推荐次入口）** | 与粘贴共用同一上传管线，额外需要拖拽高亮与落点；多文件排序要定义 | **推荐作为补充**，复用同一套校验与 pending 状态 |
| **手写 markdown 引用本地路径** | 前端读不到本机绝对路径；`![](d:\...)` 换机器即失效；还会把本机目录结构写进卡片 | **不推荐作为主入口**。只保留「通过附件选择器插入」的相对引用 |

**推荐**：粘贴截图 + 拖拽，两者共用现有 `imageDraft` 规则与上传接口；描述编辑器补同样入口（当前只有评论有）。

#### ② 存储与地址：复用附件存储，还是新建图片存储？

**推荐复用现有附件存储**，不新建图片仓库：

- 图片上传继续走 `POST /api/workspaces/:workspaceId/attachments`，返回 `id`；
- 正文引用就用现有稳定 URL：`![alt](/api/workspaces/{ws}/attachments/{id})`；
- 这正是 `imageDraft.ts:89-97` 的 `attachmentIdsFromText` 已识别的格式，评论投递链路不用改；
- 附件记录本身有 `mime_type`、大小、存储键，可做去重与清理。

**对 `markdownLinks.tsx` 的扩展口径**：

- 图片**不需要**新增 `attachment:` scheme——`markdownRenderer.tsx` 的 `img` 渲染器已经支持普通 URL，直接渲染成图。
- 若以后需要「文件引用」可点击（非图片），再加 `attachment:<id>`：在 `markdownLinks.tsx:33-40` 的 `parseMarkdownRef` 增加分支，`MarkdownSmartLink` 里按 id 打开附件/路径动作，并补 `markdownLinks.test.tsx`。
- 不建议把图片写成 `attachment:<id>`：现有 markdown 图片语法在其它 markdown 阅读器里也能退化显示，自定义 scheme 会失去可移植性。

**通用文件（一切文件）的存储**：需要给附件表加 `kind`（image / file）或独立 `files` 表，上传不限制 MIME，仍限制大小与数量；下载端点区分 inline（图片）与 attachment（其它文件）。这是新能力，不能假装已有。

#### ③ 路径引导安全性：复制路径 vs 打开文件

| 方案 | 能力 | 代价 |
|---|---|---|
| **复制路径（原型当前可用）** | 纯前端 `navigator.clipboard` + `execCommand` 兜底；无服务端改动 | 用户还要自己去找文件；路径是本机绝对路径，跨机器无意义 |
| **打开所在位置（需服务端）** | 体验最好 | 服务端缺口：需新增 `POST .../reveal`（或 open）端点；做工作区根路径校验（`realpath` 后拒绝 `..`、符号链接逃逸、工作区外路径、不存在文件）；还要处理 Windows/macOS/Linux 差异、无 GUI 的服务器、Docker 容器里没有宿主文件系统；并记审计日志 |

**取舍**：v1 只给「复制路径」，并在 UI 明说「打开所在位置需服务端能力」。原型里该按钮 `disabled` + `title` 写明缺口，不制造「已经能打开」的错觉。新增 reveal 端点单独建服务端卡（见 8.5 的 D8）。

#### ④ 图片会不会被误当证据？

会，如果允许「评论里的图 + 本机绝对路径」直接进知识库「来源与证据」。`PROV-A/B/C` 的返工就是实体路径不可移植、不可复核导致的。规避口径：

1. **证据 locator 继续只认可复核形态**：仓库相对路径 + 行号、`issue:` / `cmd:` / `agent:` 前缀；**不接受** `d:\...` 这类本机绝对路径。
2. **图片是讨论内容，不是证据本体**：评论内联图默认只是协作材料；要被引用为证据时，引用「卡号 + 评论定位 + 附件 id」，不引用本地文件路径。
3. **附件不可变 + 可追溯**：图片入附件存储后保留原始文件名、mime、大小、哈希；替换生成新 id，不覆盖旧文件。
4. **图注写来源**：原型的内联图都带 `data-caption` / `media-caption`；真实实现要求 alt/图注写清「哪张卡、哪次对比、什么结论」，避免只凭一张图下结论。
