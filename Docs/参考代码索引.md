**NousResearch/hermes-agent**（`hermes_cli/kanban_db.py`，最完整生命周期）
- `claim_task`（L2171）：`write_txn`（BEGIN IMMEDIATE + 抖动重试）内 CAS：`UPDATE tasks SET status='running', claim_lock=? WHERE id=? AND status='ready' AND claim_lock IS NULL`，rowcount≠1 即失败；同事务 INSERT task_runs + current_run_id
- `release_stale_claims`（L2317）：扫过期 claim；PID 活且心跳新鲜→延租（`heartbeat_claim` L2291）；超 1h 无心跳→判 wedged 强制回收（带 claim_lock/worker_pid/claim_expires 三重条件的 CAS），失败计数熔断防 claim↔reclaim 死循环
- 我们设计为显式领取+手动释放（无 TTL），精读其 claim CAS 与回收部分即可

## ⑥ 评论唤醒与合并（对应设计 §5.8；本地 multica 源码，只读）

链路：`D:\WorkSpaces\multica\server\internal\handler\comment.go`
`CreateComment`(L1632) → `triggerTasksForComment`(L1967) → `computeCommentAgentTriggers`(L2626) → `resolveCommentTriggerEnqueue`(L2104) → `enqueueSingleCommentTrigger`(L2561)；入队 `internal/service/task.go` `EnqueueTaskForIssue`(L1036)

要点：
- 路由条件顺序：`/note` 静默 → 显式 @agent 最优先 → @all/member 不隐式触发 → 回复 agent 父评论路由给父作者 → thread root owners → issue assignee fallback
- 静默前置 `internal/service/agent_ready.go` `AgentReadiness`：archived / 无 runtime / 离线需人工修复 → BLOCKED 不入队
- **pending 合并** `mergeCommentIntoPendingTask`(L2387) + `pkg/db/queries/agent.sql:1614 MergeCommentIntoPendingTask`：(issue,agent,thread) 唯一索引仅一条 pending；新评论并入旧 pending 的 `coalesced_comment_ids`；有界重试 4 次；不收敛如实报错，绝不伪造"已覆盖"
- CLI 身份：X-Agent-ID / X-Agent-Task-ID 请求头由 auth 中间件从 token 重打（MUL-3428）——对应我们 kb CLI 的 agent 身份传递设计

我们 §5.8 的唤醒路由比 multica 简单（单 issue 单占用 agent，无线程/多 agent 分发），精读其合并与幂等语义即可。
